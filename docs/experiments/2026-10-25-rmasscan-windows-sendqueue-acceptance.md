## 1. Итог и границы

**Windows throughput (VM): GO (VM).** CI зелёный на точном HEAD `b939cde`, итоговое ревью ветки APPROVED. Windows TX теперь отправляет пачками через Npcap sendqueue
(`TX_BATCH_FRAMES` = 64). На виртуальном e1000e стенда n2 медиана на 10 000 pps выросла с 6444.6 (OPEN) до 9964.9 pps (MET), на 100 000 pps с 6321.1 до
22532.8 pps (**OPEN**, потолок VM, честная запись по решению 8 плана). **Windows correctness (VM): перепроверена на sendqueue-коде `628fcad`: A/B PASS**
(29 и 19); прежний статус GO (VM) этим отчётом не повышается и не пересматривается. Физический NIC: **NOT RUN / OPEN**, в это GO не входит.

## 4. Топология

Стенд `n2` тот же, что в [приёмке Windows VM](2026-10-24-rmasscan-windows-vm-acceptance.md), раздел 4:

- Мост `wvb-n2` без uplink, без IP, без NAT и без forwarding; netns пира `wvp-n2`, интерфейс `lab0`.
- Гостевой NIC `Ethernet 2`, binding `\Device\NPF_{C4617223-A264-44F4-BDC8-0EA27F02CC40}`, 198.18.0.1/30, MAC `52:54:00:04:80:a9`.
- Пир 198.18.0.2, MAC `02:57:4c:3d:2e:9b`; listeners `80,443,8000-8007`, «немой» `8099`, остальные порты отвечают RST ядра. Сканы идут только в 198.18.0.2.
- seed 1, rate 100, wait 3, retries 0, shard 1/1 (часть C: 100, 1000, 10000, 100000; `stop_*` rate 1, wait 10).
- `eno1` (внешний интерфейс home-pc) снимается на каждом прогоне с фильтром лаборатории. Результат: **0 кадров лаборатории во всех прогонах всех каталогов**
  (`functional-r3` 24 прогона плюс 1 отброшенный, `failure-r2` 18 плюс 1 отброшенный, `perf-r2` 20, оба смоука, четыре теста `windows_live`; README каталогов).
  Полный `vm-lab status` с `raw_run_allowed: true` до и после каждого прогона. Ни одного срабатывания защиты, ни одного выхода с кодом 13.
- Linux-регрессия шла на minipc в замкнутом netns/veth без uplink; стенд Windows не использовался.

## 6. Результаты по частям

Счётчики из `verdict.json` (финальный; пересчитан верификатором `fb36d0c`, до него `bbda664`: `overall`, `totals` и каждый вердикт прогона неизменны, отличаются только `provenance.verifier` и текст заметки `perf_summary.notes` в `perf-r2`), проверены чтением; `verdict-628fcad.json` (вердикт, выданный верификатором `628fcad`)
совпадает с ним по `overall` и `totals` во всех трёх каталогах (проверено чтением).

### Смоук: `smoke-628fcad` — overall NOT RUN by design

`functional/` (`c01_one_addr_port_synack.run1`): 2 PASS (manifest, c01), 27 NOT RUN by design. `perf/` (`perf.100.r1`): 2 PASS (manifest, ячейка), 19 NOT RUN by design.
Ячейка: `tx_batches` 47, `tx_batch_max` 2, `tx_over_budget` 0, wire 100.8 pps. Гостевой `cargo test --locked -p rmasscan-net`: exit 0. Это не приёмка.

### Часть A: `functional-r3` — overall **PASS**, 29 PASS (FAIL 0, INVALID 0, NOT RUN 0)

Байты и порядок SYN равны фикстурам C без нормализации; pause-группы N=0/1/8/15 совпадают с непрерывным прогоном; `refuse_completed` не отправляет SYN;
`identity.tx_mode == "sendqueue"` в каждом `run.json`. Функциональные случаи содержат не больше 16 проб, пачка из двух кадров у троттлера появляется лишь примерно с 139-го кадра, поэтому пачка не формируется (кадры идут по пути `pcap_sendpacket`): `tx_batches` и
`tx_batch_max` равны 0 во всех прогонах A, `tx_over_budget` 0. Поэтому часть A доказывает паритет байтов с C на одиночном пути в sendqueue-сборке; пачки (измерено, `tx_batch_max` в `perf-r2`: 2 на 100 pps, 13 на 1k, 64 на 10k и 100k) доказывают часть C
(порядок на проводе), `windows_live` и спайк. Перезапуск: первая попытка `resume_N15` — INVALID (окно счётчика интерфейса пира; маркер конца и сброс хвоста захвата), потери tcpdump 0,
`eno1` 0 кадров, защита не срабатывала: только полнота захвата. Ветка перезапущена отдельно (`--rerun --only resume_N15`), первая попытка лежит в `runs_discarded/`, причина в
[`functional-r3/rerun-reason.txt`](2026-10-25-rmasscan-windows-sendqueue-acceptance-raw/functional-r3/rerun-reason.txt).

### Часть B: `failure-r2` — overall **PASS**, 19 PASS (18 прогонов + manifest)

- `stop_*` x4 PASS, `stop_to_outcome_ms`: stop_silent 37.4, stop_drain 44.9, stop_fullqueue 19.8, stop_load 9.0 (максимум **44.9 мс** при пределе меньше 1000 мс); после исхода SYN нет.
- `linkloss` PASS: `Failed`, `tx_sent` 40, `tx_uncertain` 1, **без checkpoint**; прогон шёл по пути одного кадра (`pcap_sendpacket`, `tx_batches` 0), поэтому случай
  частичного префикса пачки здесь не возникал и не проверен.
- `overflow_queue`, `rxloss`, `ckpt_*` x8, `perm_*` x3 PASS. `tx_over_budget` 0 и `tx_batches` 0 во всех прогонах (скорости ниже порога пачек).
- Перезапуски (оба с причиной):
  - `stop_load`: первый старт оборвался до начала захвата (ошибка сети Mac при предзапусковом Verify, `scp failed (255)`), ничего не отправлено; след в `runs_aborted/`; устаревшая блокировка suite
    на home-pc (полуоткрытая сессия мёртвого оркестратора) снята по PID; частичный каталог отброшен через `--rerun --only stop_load` (NOT RUN), затем прогон повторён.
  - `linkloss`: первая попытка INVALID (маркер конца и сброс хвоста захвата; tcpdump 177/177, потери 0, `eno1` 0, статус после допускает raw); перезапущена отдельно, первая в `runs_discarded/`.
  - Причины: [`failure-r2/rerun-reason.txt`](2026-10-25-rmasscan-windows-sendqueue-acceptance-raw/failure-r2/rerun-reason.txt).

## 8. Спайк sendqueue и решения (сводка)

Подробности и сырьё: [отчёт спайка](2026-10-25-rmasscan-windows-sendqueue-spike.md). 18 живых прогонов на стенде n2, `eno1` 0 кадров лаборатории во всех, `raw_run_allowed: true` до и после каждого.

| Вопрос | Решение | Основание |
| --- | --- | --- |
| Укладывается ли sendqueue в бюджет вызова | **GO при пачке не более 64** | n = 1/16/64 проходят правило (p99.9 не более 21 мс, max не более 42 мс); для n = 64 p99.9 и max не более 6.27 мс. 1024 и 4096 проваливают всегда |
| `TX_BATCH_FRAMES` | **64** по правилу «наибольшее n ряда 16/64/256/1024/4096, проходящее устойчиво» | n = 256 прошёл первую пару, но провалил 2 из 6 ячеек при повторе (VM имеет два режима скорости, примерно 17k и 37k pps). n = 128 вне ряда плана, измерен отдельно и прошёл; решение оставить 64 (запас p99.9 3.3 раза против 1.7-1.9 раза у 128; с RX-потоком transmit замедляется примерно вдвое) |
| Точный учёт префикса при частичном transmit | **STOP**: вся пачка `Uncertain` | При отвергнутой записи драйвер отправляет префикс (k кадров доходят до пира), но `pcap_sendqueue_transmit` возвращает **0**, а не границу записи: 84 из 84 попыток с k не менее 1. Запись `caplen 20 / len 60` принята целиком и ни разу не появилась на проводе |
| `clear()` против destroy/alloc на пачку | **`clear()` GO** | 10 000 transmit по 64 кадра: `bytes_sent` полный, пир насчитал ровно сумму, 0 дублей и потерь, утечки нет |
| Stop | **GO** | выход TX-потока после флага не более 7.73 мс, join обоих потоков не более 9.71 мс (320 раундов) |
| Один transmit под потоком мусора и RX | **44.4 мс** (один выброс на 13 431 transmit с мусором) | больше `IO_BUDGET` 42 мс, но в пределах контракта 50 мс; `tx_over_budget` его бы не посчитал (порог 50 мс); в приёмке счётчик 0 |
| Потеря линка | **«чёрная дыра»** | во время down все transmit вернули полные `bytes_sent`, 52 608 из 150 016 кадров не появились на проводе |

Следствие для продукта: любой `bytes_sent`, не равный объёму очереди (меньше, больше или 0), делает всю пачку `Uncertain`, прогон заканчивается `Failed(TxUncertain)` без checkpoint и без повтора
остатка. `bytes_sent == 0` не означает «ничего не отправлено». Правило провода при частичном transmit: `tx_sent <= SYN на проводе <= tx_sent + tx_uncertain`. Потолок VM с пачкой 64: 16.1-35.6k pps
против 6.4-7.5k pps у `pcap_sendpacket` (спайк); пачка больше 64 потолок почти не поднимает.

## 9. Ошибки и ограничения

- **VM e1000e не физический NIC.** Корректность и пропускная способность Windows на физическом NIC: **NOT RUN / OPEN**. Потолок VM не доказывает провал продукта и не подтверждает скорость на железе.
- **100k pps OPEN.** Медиана 22532.8 pps, ячейки 16.8k-29.5k (два режима скорости VM, источник переключения не установлен). Закрывается замером на целевом NIC.
- **Граница пачки измерена, не доказана как граница на физическом NIC.** `pcap_sendqueue_transmit` синхронен и не отменяем; 64 кадра выбраны по измерению на этой VM (контракт вызова
  держится на константе, а не на отмене).
- **Пути частей A и B.** В частях A и B пачки не формируются (`tx_batches` 0): функциональные случаи содержат не больше 16 проб, прогоны B шлют 1-40 кадров на скорости 1-20 pps. Пачки появляются в части C от 100 pps
  (`tx_batch_max`: 2 на 100, 13 на 1k, 64 на 10k и 100k); порядок на проводе равен плану во всех 20 ячейках (включая 100 и 1k), пачка 64 показана ячейками от 10k pps, `windows_live` и спайком; побайтный паритет с C — фикстурами части A. `linkloss` проверен на однокадровом пути: путь частичного transmit вживую не проверялся.
- **Частичный transmit: префикс не доказан.** Драйвер возвращает 0 при частично доставленной пачке, поэтому продукт делает всю пачку `Uncertain`; точный учёт префикса не используется.
- **Ошибка контролёра: `--rate-override`.** Идея `functional-batched-r1` невыполнима (раздел 6); опция попала в `628fcad` и снята в `bbda664`; ни в одном живом прогоне она не использовалась.
  Вердикты `bbda664` совпадают с вердиктами, выданными верификатором `628fcad`.
- **Флаки захвата.** «Маркер конца и сброс хвоста захвата» привёл к INVALID дважды (`resume_N15`, `linkloss`); оба случая перезапущены отдельно (раздел 6). Причина в харнессе захвата, не в продукте; корневая причина не установлена.
- **Тесты `dump` на Mac под нагрузкой.** Два теста `dump::tests::...` лаборатории иногда падают при параллельной сборке и проходят по одному (`mac-test-628fcad.log`: 640 passed, 2 failed в бинаре `rmasscan-lab` — это неполный прогон: без `--no-fail-fast` `cargo test` остановился на первом упавшем бинаре; повтор этих тестов отдельно зелёный). Известный флак.
- **`tx_over_budget` считает вызовы драйвера дольше 50 мс** (контракт `MAX_IO_TIMEOUT`), а не дольше внутреннего `IO_BUDGET` 42 мс. Выброс спайка (один transmit 44.4 мс под потоком мусора и RX) был больше 42 мс и меньше 50 мс, поэтому счётчик его бы не зафиксировал. Запас 42 мс приёмкой не измерен: `perf-r2` не хранит максимум длительности transmit, максимум `send_batch` 4.6 мс дал только `windows_live` (n=120). Адаптеры Linux и macOS (`single`) счётчик не измеряют.
- **Сборка тестов лаборатории на Linux была сломана на `628fcad` и `bbda664`.** `error[E0063]: missing fields rate_override and tx_mode in initializer of windows_suite::Suite` в Linux-тесте
  (`verification/minipc-*-628fcad.log`); живые Linux-прогоны не затронуты (релизная сборка не компилирует тесты). Исправлено `a94d695`; проверка на трёх ОС на нём пройдена (раздел 12).
- **Гостевой прогон тестов.** Первая попытка рабочей области шла на дереве без `docs/`: 54 теста лаборатории упали по этой причине; сохранена для честности (`guest-test-ws-628fcad-first.log`), заменена полным прогоном: 1019 passed, 0 failed, 34 ignored.
- **Устаревшая блокировка suite.** После обрыва ssh на home-pc остался держатель блокировки (мёртвый оркестратор); снят по PID (раздел 6, `stop_load`).
- **Linux 145 вместо 141.** Набор вырос на 4 проверки, все PASS.
- **Linux и macOS.** `max_batch` остаётся 1 (Linux `PACKET_TX_RING` и macOS пачки `write` не входят в этап); живая проверка macOS в этом этапе **NOT RUN**.
- **`kernel_drops` — нижняя граница** (счётчик очереди NPF; потери ниже NPF не видны); один сканирующий NIC, IPv4/TCP.
- **Уборка.** По записи оператора задачи 6: старые сборки и приватные target-каталоги удалены по окончании ролей (в репозитории этого следа нет).
