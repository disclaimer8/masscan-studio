# rmasscan: форматы вывода masscan, `--readscan` и строка статуса — проектный документ

Дата: 2026-11-06. Статус: проект для плана реализации. Предыдущий этап: живой скан CLI с автоопределением
(PR #49, `438e58b`, GO (stands)). Справка по байтам C: [2026-11-06-rmasscan-output-formats-c-reference.md](2026-11-06-rmasscan-output-formats-c-reference.md)
(составлена по коду upstream masscan `8e6b3b0`; ключевые места — условие интерактивной строки, ленивый заголовок,
запись JSON, 15-байтовая двоичная запись, путь `--readscan` — перепроверены по исходнику при написании этого документа).
Ссылки `файл:строка` ниже относятся к `src/` того же клона.

## 1. Намерение

Пользователь переписывает masscan на Rust («переписывание на раст масскан», «трогай masscan именно») и попросил
работать без остановок и без вопросов. После PR #49 `rmasscan` умеет живой скан, но результат печатает только
интерактивной строкой `Discovered open port N/tcp on IP`. Без файловых форматов masscan им нельзя заменить masscan в
скриптах и конвейерах: люди запускают `masscan … -oL scan.txt`, `-oJ`, `-oX` для nmap-совместимых парсеров, `-oG` для
grep, `-oB` с последующим `--readscan`. Этот этап даёт эти форматы с побайтовым паритетом с C.

Шов уже есть: трейт `Sink` в `rmasscan-cli/src/output.rs` (план autodetect: «этап 2 (форматы вывода) подключит свои
форматы»). Движок, ядро, контракты engine §0.1 и Studio не меняются.

Отношение к спеке порта: [спека порта](2026-10-23-masscan-rust-port-design.md) §3, строка «Форматы вывода», разрешала
для CLI только list, NDJSON и интерактивную строку, а XML/JSON/binary/grepable относила к «не переносить» — это было
следствием варианта B (CLI как оракул для Studio). Цель пользователя с тех пор — сам masscan на Rust, поэтому этот
документ расширяет строку для CLI (решение автора, §4 Р1). План добавит в спеку порта поправку со ссылкой сюда.

## 2. Цели, не-цели, анти-цели

**Цели.**

1. Форматы `-oL` (list), `-oJ` (json), `-oD` (ndjson), `-oG` (grepable), `-oX` (xml), `-oB` (binary), `-oH` (hostonly),
   `-oU` (unicornscan) и `--output-format none` для записей статуса TCP-порта: байты файла равны C `8e6b3b0` на тех же
   записях, кроме полей времени, которые C берёт из часов в момент записи (перечислены в §6.1).
2. `--readscan FILE…`: чтение файлов `-oB` (записи статуса TCP) и вывод через те же форматы — офлайн-конвертер и
   офлайн-оракул паритета: C читает тот же файл тем же `--readscan`.
3. Флаги masscan вокруг вывода с семантикой C: `--output-format`, `--output-filename`/`--output-file`, `-` как stdout,
   `--append-output`/`--output-append`, `--output-flush`, `--open`/`--open-only`, `--show`/`--output-show`/
   `--output-status`, `--noshow`/`--output-noshow`, `--interactive`/`--nointeractive`, `--stylesheet`, `--webxml`,
   `--status`/`--nostatus`, `--ndjson-status`.
4. Строка статуса на stderr (`main-status.c:230`, `:247`) с форматами C и завершающей «стиркой» строки
   (`main-status.c:278–279`).
5. Поведение по умолчанию не меняется: без `-o` stdout побайтно такой же, как в PR #49 (`Discovered …`, 79 колонок),
   поэтому evidence autodetect остаётся валидным.

**Не-цели (этот этап).** Баннеры и всё, что от них зависит (`--banners`, записи баннеров в форматах и в `--readscan`,
`certs`); `-oR` redis (вывод в сеть); ротация (`--rotate`, `--rotate-dir`, `--rotate-offset`, `--rotate-size`);
несколько форматов одновременно (в C тоже один, `output.c:430` TODO); IPv6-записи; записи UDP/SCTP/ICMP/ARP (движок
шлёт только TCP SYN); `-oA`/`-oN`/`-oS` (в C тоже отказ); `paused.conf` и фаза ожидания после Ctrl-C; изменения engine, core, Studio; физические NIC.

**Анти-цели.** Ни одного кадра, если файл вывода не открылся (открытие до ARP и до engine). Ни одной молча
потерянной записи: ошибка записи останавливает скан с кодом 1 (как сейчас у `Sink`). Никакого C, Python, Swift и
новых C-зависимостей (`deny.toml`, language-guard). Никакой новой сложности, которой не требует паритет: один формат
за раз, нет фоновых потоков записи, нет собственного буферного кольца.

## 3. Ограничения

- `rmasscan-cli` и `rmasscan-core` остаются `#![forbid(unsafe_code)]`; FFI только в `rmasscan-net`.
- Записи берутся из `Reply` (`remote_ip`, `remote_port`, `status`, `tcp_flags`, `ttl`); время записи ставит CLI.
  `Reply`, `Event`, `Progress` не меняются. Прогресс engine приходит раз в 250 мс (`EngineOptions::progress_interval`).
- Живые кадры только на запечатанных стендах и только в `198.18.0.0/24` (правила PR #49). Mac `sudo` выполняет только
  пользователь; этот этап построен так, чтобы окно Mac не требовалось (§7).
- Evidence для публичного репозитория пишется только в нейтральные каталоги (`mktemp -d /private/tmp/rmasscan-…`,
  на хостах — `/tmp/rmasscan-…`), privacy-grep перед копированием.
- Мерж только при зелёном CI на точном HEAD (`rmasscan`, `Studio`, `language-guard`) и одобренном итоговом ревью;
  пользователь заранее разрешил лить по результатам.

## 5. Как устроено (на уровне швов)

- Модуль `rmasscan-cli/src/output/` (вместо одного файла): тип записи `Record { timestamp, ip, port, status, reason,
  ttl }` (TCP), чистые форматтеры по одному на формат с тремя операциями C — заголовок, запись, подвал — над `Write`;
  общий конвейер-`Sink` повторяет `output_report_status`: фильтры show → интерактивная строка → ленивый заголовок →
  запись → необязательный flush; подвал в `finish`. Счётчики open/closed для подвала XML. Существующий `Interactive`
  становится веткой этого конвейера; его байты не меняются.
- Форматтеры не знают про engine и ОС: время, имена сервисов, локальное смещение и время открытия файла приходят
  параметрами — это делает их тестируемыми одинаково на трёх ОС.
- `--readscan` — отдельная операция CLI (как `-sL`, `--iflist`): читает файлы, строит `Record`, гонит их через тот же
  конвейер; не открывает адаптер, не читает маршруты, не требует прав.
- Строка статуса — отдельный компонент CLI, получает `Started`/`Progress` из того же цикла событий `run_live`,
  форматирует строки C и пишет в stderr; часы инжектируются (как в резолвере ARP).
- `args.rs`: masscan-совместимый разбор `-o<буква> FILE` до clap (clap не умеет «буква слитно с `-o`, файл следующим
  argv»), остальные флаги — clap. Отказы с текстами C (§4 Р4).

## 6. Проверка

### 6.1. Офлайн-паритет с C (CI, три ОС)

- Входные файлы `-oB` для тестов: небольшие детерминированные наборы записей (open/closed, разные IP/порты/флаги/TTL,
  порт без записи в services, граничные значения: порт 0 и 65535, TTL 0 и 255, флаги 0 и 0xFF), записанные писателем
  `-oB` rmasscan и закоммиченные.
- Эталоны: `scripts/build-oracle.sh` на minipc (оракул `8e6b3b0`, сеть отключена `unshare -n`) прогоняет C
  `--readscan` каждого входа во все форматы, с `--show open,closed` и без, плюс `-oB` (повторная запись C даёт эталон
  для писателя binary). Эталоны и манифест (sha256, argv, список масок) — в `tests/golden/formats/`.
- Поля, которые C берёт из часов в момент записи, маскируются по списку в манифесте: XML `start`, `finished time`,
  `timestr`, `elapsed`; grepable `# Masscan done at …`. Остальные байты сравниваются точно (время записей и заголовок
  binary/grepable-начала в `--readscan` детерминированы: `when_scan_started` = время первой записи, `in-binary.c:65`).
- Имена сервисов: эталон снят с `/etc/services` minipc; тест подставляет закоммиченный фрагмент services только с
  портами из входов (содержимое фрагмента сверяется с minipc при съёмке эталонов). Как именно тест подставляет файл
  (параметр библиотеки или тестовый шов бинарника, не меняющий поведение по умолчанию) — решение строителя.

### 6.2. Живой паритет (Linux netns, minipc)

- Новый набор `wire-lab.sh --suite output`: C-оракул и `rmasscan` сканируют один и тот же ответчик в netns (тот же
  seed, цели, порты с SYN-ACK и с RST), каждый во все форматы файлами, плюс `--show open,closed` и stdout `-oL -`.
  Офлайн-верификатор сравнивает множества записей (время маскировано, порядок записей нормализован, потому что порядок
  прихода может отличаться), структуру файлов (заголовок/подвал/разделители), молчание stdout при `-o…`, наличие и
  формат строк статуса на stderr, `sent` равен SYN на проводе, 0 кадров вне стенда. Вердикты PASS/FAIL/INVALID без
  повышения, evidence с хэшами — как у autodetect.
- Отказ открытия файла (каталог без прав): exit 1 и ноль кадров на проводе.
- Ctrl-C посреди скана (медленная скорость, SIGINT через ~2 с): exit 0, `[+] finished: Stopped`, файлы всех форматов
  целые (JSON закрыт `]`, XML — `</nmaprun>`, binary — 99-байтовый подвал), `sent` равен SYN на проводе. На Windows
  консольное событие по ssh не доставить: обработчик покрыт юнит-тестами, живой Ctrl-C на Windows — **NOT RUN**.

### 6.3. Регрессия живого пути

- Строка статуса меняет stderr живого скана, поэтому верификаторы autodetect (и остальные, читающие stderr живого
  CLI) должны пропускать фрагменты строки статуса (`\r`-строки) — проверяется юнит-тестами верификаторов на образцах
  stderr со строками статуса.
- Повторный прогон `autodetect-suite linux` (minipc) и `windows-suite --plan autodetect` (VM `n2`, агент поднимает и
  снимает стенд сам через `sudo -n` на home-pc): PASS. Окно Mac (`m1`) не требуется: код ниже CLI не меняется, а
  поведение CLI проверено на Linux и Windows; macOS-регрессия autodetect — **NOT RUN** этим этапом, если пользователь
  не предложит окно сам.
- Полные тесты рабочей области на трёх ОС (Mac локально, minipc, гость Windows), clippy, `cargo deny`.

### 6.4. GO

GO этапа: офлайн-паритет зелёный на трёх ОС в CI; живой паритет Linux PASS; регрессия Linux и Windows PASS; итоговое
ревью ветки одобрено; CI зелёный на точном HEAD. Вне GO: физические NIC, macOS живой прогон, баннеры, ротация, redis.

## 7. Что оставлено строителю

- Точная раскладка модулей и имена типов; как делится `args.rs` между ручным разбором `-o…` и clap.
- Шов подстановки файла services в тестах (§6.1) и способ инжекции локального смещения времени.
