## Что действительно уже есть

- Rust/Slint UI с отдельным runner и SQLite, без возврата к старой Swift-версии.
- Simulation использует настоящий engine с искусственным адаптером, без пакетов.
- Start, Pause, сохраняемый checkpoint, Resume после перезапуска, Stop.
- История, переименование, повтор настроек, удаление с подтверждением;
  собственные сохранённые профили, точный seed.
- Сортировка, фильтрация, выделение и копирование результатов; внешний Nmap
  для уточнения сервисов; CSV/JSON с данными выбранного скана.
- Helper setup и отдельная авторизация сессии; сохранение промежуточных данных
  и Interrupted при нарушениях наблюдаемого окружения.
- В ветке приёмки — сетевой preflight, coverage, unresolved/excluded адреса,
  capture и проверка результатов. macOS MacNetwork ограничен специальным
  локальным стендом; Windows/Linux полноценный raw scan из GUI не принимают.

Это перечень реализованного. Старые native-отчёты относятся к указанным в них
сборкам, а не автоматически к сегодняшним изменениям.

## P0. Согласовать основу Studio с текущим rmasscan

Неразрушающая проверка `git merge-tree --write-tree HEAD origin/main`
вернула конфликты в **11 файлах rmasscan-net**:

- `Cargo.toml`, `src/lib.rs`;
- `src/arp_resolve.rs`, `src/arp_resolve_tests.rs`;
- `src/discover.rs`, `src/discover_tests.rs`;
- `src/macos/route.rs`;
- `src/route_parse.rs`, `src/route_parse_tests.rs`;
- `src/windows/mod.rs`, `src/windows/sys.rs`.

Это не косметический конфликт UI. Ветка Studio использует `PhysicalTargets`,
`PhysicalRoutePlan`, `NeighbourReport`, `ExcludedReason` и отдельную подготовку
маршрутов/соседей; в текущем main публичная поверхность discovery устроена иначе
(`Targets`, `Detected`, `NextHop`, `detect`, `arp_resolve`). Старые network_plan
и neighbours из ветки Studio в main отсутствуют. Выбрать весь файл «ours» или
«theirs» недостаточно: можно потерять исправления автодетекта или данные coverage.

Нужен фиксированный SHA сканера и согласованный контракт:

1. Какие API дают ограниченный план целей, маршрут/source/interface и MAC
   каждого назначения, как представлены исключения и неразрешённые соседи.
2. Какие части относятся к Studio, а какие остаются в rmasscan-net; не создавать
   вторую копию алгоритма обнаружения внутри GUI.
3. Как план связан с identity/checkpoint, отменой подготовки и проверкой
   изменений сети. Сохранить старую историю и корректный отказ несовместимого Resume.
4. На этом контракте собрать Studio, проверить Simulation и headless сценарии,
   затем пакет и отдельную native-приёмку.

**Критерий готовности:** одно проверяемое дерево с современным движком,
воспроизводимая сборка, точные версии/хеши, зелёные проверки обеих рабочих областей.
Текущие изменения сканера Клода в этом проходе не редактировались.

## P0. Завершить обычный сетевой запуск через Studio

Нынешний пользовательский путь заканчивается ограничением стенда. Нужны:

- понятный выбор реального интерфейса/источника и поддерживаемого backend;
- проверка настроек, авторизация, подготовка соседей и Start без лабораторных
  билетов и служебных команд в обычном пользовательском сценарии;
- честное отображение «не сканировалось», «нет ответа» и полученных TCP состояний;
- Complete, Stop→Start и Pause→Resume в одном окне, Resume после перезапуска;
- корректный Interrupted при потере сети, смене маршрута, sleep/wake и потере helper;
- отдельная приёмка на конкретном разрешённом физическом устройстве.

Текущий `--smoke-single-target` — инструмент приёмки, а не готовый обычный flow.
Отчёт 03.11 оставлял незавершёнными supervisor, точную пакетную provenance,
live capture/GUI attempt и cleanup. Исправление кнопок ниже этот этап не закрывает.
Ни сеть отеля, ни обнаруженный шлюз нельзя подставлять вместо заданной цели.

## P1. Довести интерфейс и установку

1. Первый запуск должен показывать доступный режим. Неактивный профиль не должен
   позволять Start; Simulation не должна выглядеть как результат реального скана.
2. Проверить обычными мышью/клавиатурой: New scan, валидацию, отмену действий,
   helper setup, отказ и повтор авторизации, History, Repeat, профили и экспорт.
3. Проверить фокус, resize/scroll, пустые результаты, длинные ошибки и native
   Save dialog. Автоматические callbacks не закрывают эти проверки.
4. Развести понятную причину недоступности: профиль не поддерживается ОС,
   helper не установлен, сессия не авторизована, маршрут не готов.
5. Проверить обновление с точным новым helper и существующей историей. Тестировать
   отдельную базу; не мигрировать рабочую пользовательскую историю ради smoke.

## P1. Решить, какие новые возможности engine выходят в GUI

Не нужно превращать каждый CLI-флаг в отдельный элемент окна. Приоритет —
параметры, которые нужны обычному скану и должны переживать History/Repeat/Resume.

| Область | Сейчас в Studio | Следующая работа |
| --- | --- | --- |
| Targets/ports/exclusions/rate/seed | Есть, TCP/IPv4, ограничения по профилю | Согласовать с новым планировщиком, сохранить проверку до Start |
| Wait | В preview/подготовке фиксировано 3 секунды | Если открывать настройку — провести через Job, identity, profiles, history и checkpoint |
| Retries/shard/multi-adapter и другие scan-control параметры | GUI их не предоставляет | Выбрать продуктовый набор после общей интеграции; не обещать поддержку только по наличию CLI |
| Форматы результатов | Studio CSV/JSON, отдельная семантика coverage и inspection | Не подменять их CLI-экспортами; новые форматы добавлять с явными правилами потери/сохранения метаданных |
| Платформы | Офлайн UI переносим, raw GUI ограничен macOS стендом | Или явно первый macOS-релиз, или самостоятельная network/helper-приёмка Windows и Linux |

Ранее согласованный интерфейс — библиотека engine внутри Rust runner и
типизированный IPC. Не возвращать парсинг stdout внешнего masscan ради быстрого
подключения новых функций CLI.

## Исправлено в этом проходе

В `studio-ui/ui/main.slint` и `studio-ui/src/network_tests.rs`:

1. **Start учитывает доступность каждого профиля.** Раньше условие проверяло
   gate только MacNetwork: MacFeth с `mac_feth_open=false` и неизвестные индексы
   проходили UI-проверку. Runner всё равно отказывал, но кнопка вводила в заблуждение.
2. **Переносимый начальный режим — Simulation.** До явной настройки macOS-профиля
   окно выбирало MacFeth, который недоступен на Windows/Linux. Обычный адрес
   `192.0.2.1` сразу получал ошибку о единственном разрешённом feth peer.
   macOS-инициализация по-прежнему явно выбирает свой включённый профиль.

Два теста сначала воспроизвели ошибки, затем стали проходить. Проверка охватывает
открытые/закрытые профили, неизвестный индекс, активную попытку, невалидные настройки
и доступную Simulation. Это отображение возможностей, не ослабление runtime-gate.
