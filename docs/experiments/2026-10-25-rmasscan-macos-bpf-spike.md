# Эксперимент: BPF на macOS (feth4201 <-> feth4202): раскладка, дедлайны, свои кадры, TX, bs_drop, Stop (2C, задача 3)

Дата: 2026-10-25. Эмпирическая проверка ОДНОЙ связки: macOS 27.0.1 (26A434), Darwin 27.0.0 (xnu-13432.1.9), Apple M4 Pro
(arm64), запечатанный стенд `m1` (пара `feth`, копирование в ядре). Это не физический NIC и не другая версия macOS.

Код: `rmasscan/crates/rmasscan-net/src/macos/spike.rs` (`cfg(all(target_os = "macos", test))`, все тесты `#[ignore]`), коммит
`test(net): macOS BPF deadline, own-frame and drop-counter spike` на базе `24e3f4f`. Сырьё:
[`2026-10-25-rmasscan-macos-bpf-spike-raw/`](2026-10-25-rmasscan-macos-bpf-spike-raw/) (`MANIFEST.sha256`; проверка:
`shasum -a 256 -c MANIFEST.sha256` из каталога raw). Оркестратор: `tools/run_spike.sh.txt`, окружение: `env.txt`.
Все тайминги из `runs/<run>/out/*.log` и `*.csv`.

## Поправки к плану, которые нашёл спайк

1. `bh_hdrlen = 18` на этом ядре (план писал 20). Адаптер Task 4 исходит из 18 и шагает по `bh_hdrlen` + `BPF_WORDALIGN`: верно.
2. **Listener на `198.18.0.2:80` без root невозможен**: `bind` на конкретный адрес порта < 1024 даёт `EACCES` (`rmasscan-lab peer listen` -> `Permission denied (os error 13)`; `nc -l 198.18.0.2 80` то же); на `0.0.0.0:80` и на `198.18.0.2:8000` работает. Безпривилегированное исключение macOS распространяется на wildcard-bind, не на привязку к IP. Следствие: case-листы с портами 80 и 443 на Mac без root невозможны; открытые порты стенда без root это `8000-8007`. Неудачная попытка r01 сохранена в `failed/r01-stand-path-listener80-EACCES`.
3. Предел размера записи в BPF `feth` лежит между 1518 и 1600 (не 1514). Не влияет на продукт (свой предел 1514).
4. `debug.bpf_maxbufsize` = 524288, но `BIOCSBLEN 4 MiB` дал `BIOCGBLEN = 4194304` (sysctl не жёсткий потолок для этого запроса на этом ядре). Адаптер всё равно читает `BIOCGBLEN`.
5. Ядро отвечает RST не на каждый SYN подряд: из 20 SYN на закрытый порт без паузы пришло 10 записей (возможно с ретрансмитом SYN-ACK :8000), из 100 SYN 74 RST (ограничение скорости RST ядром, причина не доказана). Для приёмки: RST-ответы под нагрузкой не полны по построению.
6. Свидетели: tcpdump на `feth4202` в r08 захватил 2 089 470 из 2 200 133 (flood 20k pps + 60 раундов TX); `dropped by kernel` 0, но кадры, не успевшие в файл к SIGINT, недосчитаны. r08 `peer.pcap` не копирован (140 МБ), sha256 и размер записаны. Для остальных прогонов `captured == received` или разница 1 кадр на SIGINT (r01: 36 из 37).

## Открытый риск: блокирующий `write()` (замечание ревью)

XNU `bpfwrite` игнорирует `ioflag`, поэтому `O_NONBLOCK` на запись не действует, а mbuf выделяется с `MBUF_WAITOK`: синхронный
`write()` теоретически может блокироваться. Измерено на feth: максимум `write()` = 70.3 мкс на 206 000 вызовов (5000 подряд, 1000
по 1 кадру/мс, 200 000 подряд), блокировок не наблюдалось, `EAGAIN`/`ENOBUFS` 0. Stop в серии `write`: TX-поток видит флаг за
max 30.5 мкс. Это измерение копирования в ядре между двумя feth без нехватки mbuf. Механизм риска (`bpfwrite` ничего не знает об
`ioflag`, `bpf_movein` выделяет mbuf с `MBUF_WAITOK`) срабатывает до драйвера и потому относится к ЛЮБОМУ интерфейсу, включая
`feth`, при нехватке mbuf; на физическом NIC к нему добавляется обратное давление драйвера. Спайк верхней границы НЕ даёт: на feth
блокировок не наблюдалось, граница не доказана, пункт остаётся открытым (исправлено по итоговому ревью, ранее риск был назван
риском физического NIC).

## Окружение и изоляция

- Стенд `m1`: `feth4201` (сканер, MAC `02:ac:00:00:00:01`, без IP) <-> `feth4202` (пир, `198.18.0.2/30`, MAC `02:ac:00:00:00:02`);
  манифест `/var/run/rmasscan-lab/m1.json` (sealed); uplink `en0`. MAC в ifconfig маскируются (`02:00:00:00:00:00` у процессов от ad-hoc
  подписи): использованы константы плана, MAC на проводе сверены в кадрах.
- Перед и после КАЖДОГО прогона `macos-lab --run-id m1 status` (сборка `24e3f4f` контролёра): rc 0, `raw_run_allowed: true`,
  `bpf_access: "granted"` (`pre-status.json`/`post-status.json` в каждом `runs/<run>/`, `gate.txt`). Нарушений нет.
- Uplink-захват `tcpdump -p -n -i en0 -U -w uplink.pcap` с фильтром лаборатории
  `ether host 02:ac:00:00:00:01 or ether host 02:ac:00:00:00:02 or ether host 02:ac:00:00:00:11 or net 198.18.0.0/30`; 0 кадров в
  11 зачётных прогонах + 2 неудачных; tcpdump rc 0 после SIGINT, `dropped by kernel` 0, pcap читается целиком.
  **Idle-контроль (r00, 5 с)**: `0 packets captured / 2005 packets received by filter / 0 dropped`: на macOS «received by filter»
  считает пакеты ДО фильтра, поэтому ненулевое число при 0 пойманных ожидаемо; критерий «0 кадров» это число кадров в отфильтрованном pcap.
- Свидетель пира: `tcpdump -p -n -i feth4202 -U -s 128 -w peer.pcap` в каждом прогоне, кроме idle.
- Запись только через `Dev::send` с `assert_lab_frame`: сторона сканера dst MAC `02:ac:00:00:00:02`, src `…:01` или `…:11`, dst IP
  `198.18.0.2`; сторона пира только ethertype `0x88b5` от `…:02` к `…:01`. Интерфейсы кроме `feth4201/4202` отвергаются.
- Прогоны: r00 idle uplink; r01 стенд; r02 дедлайн idle; r03 wakeup; r04 свои кадры; r05 дедлайн под потоком; r06 TX; r07 health;
  r08 Stop; r09 длинные дедлайны (нагрузка CPU); r10 длинные дедлайны (тихо). Два неудачных, сохранённых в `failed/`: r01 (listener :80,
  EACCES) и r06 (утверждение EMSGSIZE на 1515, неверное; серии TX в нём валидны). r01-r05, r07, r08 выполнены на бинарнике,
  собранном до правки `live_tx` (проба размеров) и до мелкой правки clippy в `flood`; код этих тестов не менялся. Хэш итогового
  бинарника в `env.txt` относится к r06, r09, r10.
- Python не использовался.

## Ограничения

- Одна версия macOS, один Mac, feth (копирование в ядре): потери ниже BPF, блокировка `write` и сон/пробуждение не проверены.
- Overshoot зависит от нагрузки CPU: приведены оба прогона (r09 с совпадением по времени с `cargo`-сборкой, r10 тихий).
- Нагрузка пира (20k pps, 200k) создавалась в процессе спайка потоком на `feth4202` (pacing по спин-ожиданию), `peer inject` из lab на Mac не работает.
- Тест `live_tx` измеряет только размеры вплоть до 16384; точный порог между 1518 и 1600 не искали.
