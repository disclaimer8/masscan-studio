# Эксперимент: Npcap 1.90 TX/RX, дедлайны и счётчик потерь на Windows VM (2B-Windows, задача 2)

Дата: 2026-10-24. Это эмпирическая проверка ОДНОЙ связки (Windows 11 Pro 10.0.26300 x64, Npcap 1.90
AdminOnly=1, виртуальная Intel 82574L/e1000e на KVM/QEMU) на изолированном стенде `n2`. Это не
универсальная гарантия для других версий Npcap, физических NIC, пропускной способности и Wi-Fi.

Код: коммит `53fe366` (`test(net): Npcap TX/RX deadline and drop-counter spike`), собран и
запущен из `git archive` ровно этого коммита. Сырьё: [`2026-10-24-rmasscan-stage2b-windows-spike-raw/`](2026-10-24-rmasscan-stage2b-windows-spike-raw/)
(`runs/<run>/` = логи гостя, CSV каждого вызова, pcap пира и eno1 с хэшами, status.json до/после,
`MANIFEST.sha256`).

## Решения

| Пункт | Решение | Чем подтверждено |
|---|---|---|
| RX nonblocking, дедлайн ≤50 мс | **GO** с условием: внутренний бюджет адаптера должен быть меньше 50 мс на запас планировщика | Один `pcap_next_ex` в nonblocking: p50 6-15 мкс, макс 2.7 мс. Вызов с собственным абсолютным дедлайном 50 мс: Hybrid-ожидание p50 50.03 мс, макс 53.4 мс (перерасход до 3.4 мс); при потоке кадров макс 4.3 мс. Ни одного зависания |
| TX ограничен (`pcap_sendpacket`) | **GO (эмпирически)** с остаточным риском | 33 000+ синхронных отправок: все rc=0, p50 113-256 мкс, p95 ≤1.5 мс, макс 22.6 мс (одна из 5000 в idle). Ни одна не приблизилась к 50 мс. Отмены нет: проверка стопа возможна только между вызовами |
| RX health (`Some(n)` из `pcap_stats`) | **GO** с условиями (ниже) | Per-handle, кумулятивный, чтение не сбрасывает; 0 на чистом прогоне; при переполнении `ps_drop` равен независимо измеренной потере ТОЧНО (4 прогона); вызов ≤1.3 мс; ошибка запроса даёт rc<0 |
| Stop ≤1 с | **GO** | TX-поток видит stop за p50 0.1 мс / макс 1.4 мс; RX-поток макс 51.7 мс (в худшем случае досиживает текущий вызов recv); оба потока присоединены за макс 53.4 мс |
| Реальный unplug lab-линка | **NOT RUN в полном виде** | `ip link set wvt-n2 down` на хосте НЕ меняет состояние адаптера в госте: `Status=Up` весь прогон, `pcap_sendpacket` по-прежнему rc=0, пир не получил ни одного кадра (чёрная дыра). Гостевой разрыв (QMP `set_link`) вне разрешённых действий |
| sleep/wake | **NOT RUN** | `powercfg /a`: доступны только Hibernate и Fast Startup, S1/S2/S3/S0ix недоступны. Гибернация выключает VM, а не усыпляет: риск для стенда без пользы для проверки |

## Что именно измерено

### Окружение
- Guest: Windows 11 Pro 10.0.26300 x64; Npcap 1.90 (`npcap.sys` 1.90, служба Running, `AdminOnly=1`,
  `pcap_lib_version` = «Npcap version 1.90, based on libpcap version 1.10.7 (64-bit time_t)»,
  wpcap.dll sha256 `332f81cc…96a9f`, Packet.dll 5.1.90.1020), rustc/cargo 1.99.1 MSVC, сборка `debug`.
- Lab NIC «Ethernet 2», MAC `52:54:00:04:80:a9`, `\Device\NPF_{C4617223-A264-44F4-BDC8-0EA27F02CC40}`,
  198.18.0.1/30; пир `wvp-n2/lab0` 198.18.0.2, MAC `02:57:4c:3d:2e:9b`. Управляющий NIC не открывался.
- Часы гостя были на +7 ч (UTC читался как местное время часового пояса UTC-7). До: `UtcNow`
  18:24:20Z при Mac 11:24:16Z, пояс «Pacific Standard Time», `w32time` Stopped. Исправлено `tzutil /s "UTC"`,
  `Start-Service w32time`, `w32tm /resync /force` (синхронизация сообщила «no time data available»,
  NAT не пропускает NTP, но RTC в UTC верен). После: 11:24:41.147Z при Mac 11:24:41Z; повтор в конце: 11:46:42.977Z / 11:46:43Z.
  Перезагрузка не потребовалась. Скрипты: `tools/clock0.ps1`, `tools/clock1.ps1`.

### Изоляция (на каждом из 10 зачётных прогонов)
Перед прогоном: гостевой Verify, `record-guest`, полный `status` с `raw_run_allowed: true`; после: снова `status`
(все `pre`/`post` = true, нарушений изоляции нет). Отправка только с указанного NPF-устройства и только на 198.18.0.2
(`assert_lab_frame` перед каждым `send_raw`: dst MAC пира, src MAC lab NIC, dst IP 198.18.0.2). Захваты:
- пир: `ip netns exec wvp-n2 tcpdump -i lab0 -n -U -s 96 -w peer.pcap 'not ether proto 0x88b5'` и счётчик мусора
  `tcpdump -i lab0 -w /dev/null 'ether proto 0x88b5'`;
- home-pc: `tcpdump -i eno1 -n -U -s 96 -w eno1.pcap 'net 198.18.0.0/30 or (arp and (host 198.18.0.1 or host 198.18.0.2)) or ether host 52:54:00:04:80:a9 or ether host 02:57:4c:3d:2e:9b or ether proto 0x88b5'`.
Итог eno1: **0 кадров во всех 10 прогонах**. Единственное изменение стенда: `ip link set wvt-n2 down/up`
в r05, r09, r10 (разрешённый тест unplug), TAP возвращён вверх, `status` после каждого прогона зелёный.
(Два первых запуска overflow с ошибкой передачи параметров оказались пустыми: пакеты не уходили, их каталоги удалены и перезапущены; два предварительных прогона на коммите 97cca5c до правки кода тоже удалены.)

### Что узнали о поведении Npcap
1. **Каждый handle имеет собственные счётчики.** TX-handle, который никто не читает, копил `ps_recv` = весь трафик и
   `ps_drop` ≈ 98% (e.g. 52 986 из 53 816). Новый handle после потока стартует с `0/0` (`fresh_C_after_flood`).
   Следствие для задачи 3: TX-handle открывать с минимальным буфером (в споке 64 KiB) или с фильтром «ничего»
   (`pcap_compile`/`pcap_setfilter` в таблицу символов пока не входят).
2. **RX-handle видит собственные кадры TX** (1000 из 1000 в `rx_after_tx_paced`, `own_tx=1000`). Фильтрация собственного TX
   (по `src MAC` из binding) нужна в адаптере; сигнала «outgoing» нет.
3. `pcap_sendpacket` синхронный, rc 0/-1. Ошибки: пустой кадр rc=-1 «The number of bytes to be sent must be positive»;
   кадр 9000 байт rc=-1 «PacketSendPacket failed … (20)». Исход при rc=-1 неизвестен по тексту: по контракту `Uncertain`.
   `rc=0` не доказывает доставку: при отключённом на хосте TAP все отправки rc=0, пир получил 0 кадров.
4. Ошибка открытия несуществующего устройства: `pcap_create` возвращает NULL, errbuf «Error opening adapter: Network
   interface was not found. (2150891563)» (144 мкс), а не отказ `pcap_activate`.

### RX health: честность счётчика
Опыты `live_overflow`: медленный читатель A (буфер 32 KiB, не читает 6 с), независимый счётчик B на том же устройстве (буфер 64 MiB),
сравнение с количеством из потока и сверка после дренажа:

| Прогон | отправлено пиром | дошло до NPF (B recv) | A recv | A drop | потеря A по независимому счёту (B−A) | A прочитал | `recv−drop` = прочитано |
|---|---|---|---|---|---|---|---|
| r06 максимум (354 kpps) | 200 000 | 62 972 | 62 972 | 62 562 | 62 562 | 410 | да |
| r07 50 kpps | 200 000 | 200 000 | 200 000 | 199 590 | 199 590 | 410 | да |
| r08 20 kpps, буфер 1 MiB | 100 000 | 100 000 | 100 000 | 86 892 | 86 892 | 13 108 | да |

- `ps_drop` = независимая потеря ТОЧНО (не меньше, не больше); `ps_recv` включает потерянные кадры.
- Кумулятивность: три чтения подряд идентичны, чтение после дренажа не меняет значения, значения по серии 250 мс монотонны.
  `ps_ifdrop` всегда 0, `ps_capt/sent/netdrop` не заполняются.
- Чистый прогон: 0 (r03, r05, r09; `ps_recv` пира = `ps_recv` handle: 38 094 = 38 094).
- Unplug: `ps_recv` перестаёт расти (остаются фоновые кадры гостя), `ps_drop` замирает (15 235), ошибок нет; после возврата
  TAP рост возобновляется, значение не сбрасывается.
- Ошибка запроса: `pcap_stats` на неактивированном handle: rc=-3, geterr «This handle hasn't been activated yet», 13 мкс. Адаптер обязан
  превращать rc<0 в `Err`, а не в 0 или `None`.
- Оборот u32: `ps_drop` и `ps_recv` 32-битные. `DropCounter` (handle.rs) суммирует дельты `wrapping_sub`; верно, пока между двумя
  чтениями < 2^32 потерь (при периоде health 250 мс недостижимо), тесты на оборот и на сброс (сброс похож на оборот и даёт
  огромную дельту, то есть безопасный RxLoss). Принудить оборот в живую нельзя, проверено юнит-тестами.

**Ограничение, которое нельзя скрывать.** В r06 пир отправил 200 000 кадров, до NPF дошло 62 972: 137 028 кадров потеряны ниже Npcap
(гипервизор/эмулированный e1000e), и ни `ps_drop`, ни `ReceivedDiscardedPackets` гостевого адаптера (0) их не показали.
Так же слеп `ps_ifdrop` на любом NIC. Счётчик Npcap честен для очереди NPF (приём-локальная потеря, которую описывает контракт
`Rx::health`), но не для потерь в кольце драйвера. Для задачи 3: рассмотреть добавление дельты `InDiscards/InErrors`
интерфейса (`GetIfEntry2`) в `kernel_drops`; на этой VM она не проверяема (счётчик остаётся 0 при потере на хосте).
Решение GO относится к потере в очереди NPF.

## Рекомендации для задачи 3 (не ослабляя контракт)
- RX: nonblocking `pcap_next_ex` + собственный абсолютный дедлайн, ожидание Hybrid (сон 1 мс пока осталось >3 мс, затем `yield_now`),
  внутренний бюджет, например `min(timeout, 50 мс) − 5 мс`, так как наблюдались перерасходы до 3.4 мс.
- TX: `pcap_sendpacket` один кадр синхронно, rc=0 → `Sent`, rc<0 → `Uncertain` (без анализа текста). Никаких sendqueue и worker'ов.
- Health: baseline `ps_drop` при открытии, `DropCounter::update` на каждом вызове, rc<0 → `Err`.
- Не принято по результатам: настоящий гостевой unplug, sleep/wake, физический NIC, пропускная способность, release-сборка.
