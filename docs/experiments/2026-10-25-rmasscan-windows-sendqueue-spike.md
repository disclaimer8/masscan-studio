# Эксперимент: Npcap sendqueue на Windows VM, тайминг пачки, граница частичного transmit, повторное использование очереди, Stop (задача 3)

Дата: 2026-10-26 (часы Mac, UTC). Это эмпирическая проверка ОДНОЙ связки (Windows 11 Pro 10.0.26300 x64, Npcap 1.90
AdminOnly=1, виртуальная Intel 82574L/e1000e на KVM/QEMU, 6 vCPU на Ryzen 9 7900X3D) на изолированном стенде `n2`. Это не
универсальная гарантия для других версий Npcap, физических NIC и Wi-Fi.

Код: тесты `live_sendqueue_*` в `rmasscan/crates/rmasscan-net/src/windows/live.rs` (`#[ignore]`, только Windows).
Они работают напрямую с `SendQueue`/`PcapHandle::transmit_raw` задачи 2 (адаптера в них нет), TX handle в продуктовой
конфигурации (snaplen 64, буфер 64 КиБ, фильтр `ret #0`). Коммиты:
- `61c1126` `test(net): Npcap sendqueue timing, partial-transmit boundary and stop spike`: прогоны r00-r04;
- `53afec8` `test(net): sendqueue spike reuse test preallocates its logs`: прогоны r05-r15;
- `3954b14` `test(net): sendqueue spike reuse test touches its log pages up front`: прогоны r16, r17.
  Обе правки только в журналах теста reuse (см. «Повторное использование очереди»). Под `53afec8` и `3954b14` в ветке лежит коммит задачи 4
  `2f322c3` (адаптер); спайк его не исполняет: разница `SendQueue`/`transmit_raw` между `61c1126` и `3954b14` только `cfg`/`dead_code`, поведение то же.

Каждый прогон собран из `git archive` точного коммита на госте (`C:\Users\lab\src\rmasscan-<sha>`, debug/test-профиль
проекта «optimized + debuginfo»); `cargo clean -p` трёх рабочих crate перед сборкой (mtime из архива иначе дал бы устаревший
бинарь). sha256 тестового exe: `61c1126` = `907f1f4c…bd72b64`, `53afec8` = `1c31bf16…4811e1`, `3954b14` = `a6803a84…4dc260` (в `runs/*/guest-out/*.run.txt`).
`cargo clippy --locked -p rmasscan-net --all-targets -- -D warnings` на госте для `53afec8` и `3954b14`: чисто.
Сырьё: [`2026-10-25-rmasscan-windows-sendqueue-spike-raw/`](2026-10-25-rmasscan-windows-sendqueue-spike-raw/) (`runs/<run>/`, `tools/`,
`MANIFEST.sha256`; проверка: `shasum -a 256 -c MANIFEST.sha256` из каталога raw).

## Решения

| Пункт | Решение | Чем подтверждено |
|---|---|---|
| Укладывается ли sendqueue в бюджет контракта | **GO, при пачке не более 64** | n = 1/16/64 проходят правило (p99.9 ≤ 21 мс, max ≤ 42 мс, `bytes_sent == bytes_queued`) во всех 4 ячейках формального ряда (idle и flood, два прогона): n = 64 p99.9 ≤ 6.27 мс, max ≤ 6.27 мс. n = 1024 и 4096 проваливают всегда (p99.9 37-82 мс и 122-320 мс). STOP по правилу («даже n = 16 не укладывается») не наступает |
| `TX_BATCH_FRAMES` (правило: наибольшее n ряда, проходящее в обоих условиях) | **64** | n = 256 прошёл в первой паре (r01 idle p99.9 19.95 мс, r02 flood 9.96 мс), но НЕ воспроизвёлся: r10 flood p99.9 **21.93 мс** (FAIL), r07 idle на 1000 циклах p99.9 **21.04 мс** (FAIL). Поэтому наибольшее n, проходящее устойчиво, это 64. Лимиты не ослаблены. Если принять только первую пару r01/r02, правило даёт 256 (см. «Выбор пачки») |
| Точный учёт префикса при частичном transmit | **STOP** (вся пачка `Uncertain`) | При отвергнутой записи драйвер **отправляет префикс (k кадров доходят до пира, остаток после отвергнутой записи не доходит), но `pcap_sendqueue_transmit` возвращает 0**, не границу записи: во всех 84 попытках с k ≥ 1 (2 отвергаемых кандидата × 21 × 2 прогона r03, r06). `bytes_sent` не на границе, а число принятых драйвером кадров через него не восстановить. Запись `caplen = 20, len = 60` драйвер принимает целиком (`bytes_sent == bytes_queued`), т.е. отвергнутой не получилось |
| `clear()` против destroy/alloc | **`clear()` GO** | 10 000 transmit по 64 кадра с `clear()` и 1 000 с destroy/alloc на пачку (r16): `bytes_sent` полный во всех 11 000, пир насчитал ровно Σn (704 000, 0 дублей, 0 потерь), рост рабочего набора между 10% и 100% **8 192 Б** (clear) и **0 Б** (destroy/alloc) при пределе 1 МиБ, handles 145. Длинный прогон 40 000 + 1 000 вызовов (r17, 2.62 млн кадров): рост **−16 384 Б** (плато 10.82 МБ), handles 139-141. Расхождений при `clear()` нет |
| Stop ≤ 1 с | **GO** | 60 + 60 + 200 раундов со случайным моментом: выход TX-потока после флага ≤ 7.73 мс (≤ одного transmit), join обоих потоков ≤ 9.71 мс (предел 1 с); transmit не усечён ни разу |
| Потеря линка (QMP `set_link`, информационно) | **«Чёрная дыра» подтверждена** | во время down (10 с) все transmit вернули полные `bytes_sent`, длительности нормальные (макс 6.55 мс), 52 608 из 150 016 кадров на проводе не появились (822 вызова пропали целиком, ни одного частично); NIC гостя стал `Disconnected`. Это информация для части B `linkloss`, не критерий GO |
| `eno1` | **0 кадров лаборатории во всех 18 прогонах** | `eno1.pcap` = 24 байта (заголовок pcap) в каждом прогоне, счётчик orch.sh 0 |
| Стенд | `raw_run_allowed: true` до и после каждого прогона | `status-pre.json`/`status-post.json` в каждом `runs/<run>/`; `guest_verify_nonce` совпадает с nonce прогона |

### Выбор пачки

- Правило брифа: наибольшее n ряда 16/64/256/1024/4096, у которого в обоих условиях p99.9 ≤ 21 мс и max ≤ 42 мс.
- Первая пара (r01 + r02) даёт n = 256 (p99.9 19.95 мс idle, 9.96 мс flood). Повтор (r09 + r10) сломал эту оценку: flood p99.9 21.93 мс.
  Дополнительные 1000 вызовов (r07) дали idle p99.9 21.04 мс, max 22.8 мс. Из шести пар «условие × прогон» для n = 256 FAIL в двух.
- Причина нестабильности: у VM два режима скорости, ~17k pps («медленный») и ~37k pps («быстрый»). Режим не определяется условием
  (r01 idle медленный, r02 flood быстрый, но r10 flood медленный, r08 flood быстрый, r04 idle быстрый, r05 idle медленный; r09 в середине прогона переключился: n = 1024 ~27k, n = 4096 ~40k).
  При 256 кадрах «медленный» режим даёт p50 14-15.5 мс и p99.9 около лимита 21 мс. Источник переключения не установлен (гипотезы: частота/простой ядер хоста и порог пробуждения потока ввода-вывода QEMU); это ограничение VM, не продукта.
- n = 64 проходит всегда: наихудший p99.9 6.27 мс (r09 idle), наихудший max 6.27 мс, то есть 3.3-кратный запас по p99.9 и 6.7-кратный по max.
- **Результат: `TX_BATCH_FRAMES = 64`** (предварительные 256 из плана не подтверждены устойчиво). Потолок VM при 64 кадрах: 16.1-35.6k pps против ~6.4-7.5k pps у `pcap_sendpacket`;
  выигрыш 2.5-5×. Пачка больше 64 потолок почти не поднимает (при n = 256 то же 16-37k pps в тех же режимах): стоимость определяет эмуляция e1000e, а не число вызовов.
  Лимиты не менялись.

## Частичный transmit: граница записи (`live_sendqueue_partial_boundary`, r03 и r06)

Очередь: k корректных SYN (7 × 20 раз, а также k = 0 и k = 255), одна отвергаемая запись, m = 5 корректных. Три кандидата по очереди.
Для каждой попытки в CSV: `bytes_queued`, граница k `Σ_{j<k}(16 + caplen_j)`, `bytes_sent`, текст `pcap_geterr`; пир по seq называет каждый дошедший SYN.

| Кандидат | `bytes_sent` | пир: префикс (k) | пир: остаток после записи (m) | `pcap_geterr` |
|---|---|---|---|---|
| кадр 9000 байт, k = 7 (×20) | **0** (граница 518) | 7 из 7 | 0 из 5 | «Error queueing packets: The system cannot find the device specified. (20)» |
| кадр 9000 байт, k = 255 | **0** (граница 18 870) | 255 из 255 | 0 из 5 | то же (20) |
| кадр 9000 байт, k = 0 | 0 (граница 0, совпадение тривиально) | | 0 из 5 | то же (20) |
| `caplen = 0`, k = 7 (×20) | **0** (граница 518) | 7 из 7 | 0 из 5 | «Error queueing packets: The parameter is incorrect. (87)» |
| `caplen = 0`, k = 255 | **0** (граница 18 870) | 255 из 255 | 0 из 5 | то же (87) |
| `caplen = 20, len = 60`, k = 7 (×20), 0, 255 | `bytes_queued` полностью | все | 5 из 5 | текст (87) остался от предыдущего вызова, это не ошибка этого вызова |

Результат одинаков в r03 и r06 (66 попыток в каждом, 132 всего).

- **Драйвер обрабатывает записи по порядку**: префикс до отвергнутой записи уходит на провод, записи после неё нет. Это совпадает с гипотезой «останов на отвергнутой записи».
- **Но возвращаемое число байт при ошибке ioctl равно 0**, а не `Σ_{j<k}(16 + caplen_j)`. Для k = 255 transmit занял 16 мс, то есть кадры реально шли, а ответ «0 байт».
- Следствие: «`bytes_sent` на границе записи» не наблюдается ни разу при ненулевом префиксе. Критерий STOP брифа («`bytes_sent` не на границе») выполнен для обоих кандидатов, которые драйвер отвергает.
  Точный учёт префикса живьём не подтверждён; единственное, что можно честно утверждать: `bytes_sent == bytes_queued` значит «драйвер принял всю очередь», любое другое значение (включая 0) значит «исход неизвестен, часть кадров могла уйти».
- Попутное наблюдение: запись `caplen = 20` (< 34 байт, runt) драйвер **принимает** и считает в `bytes_sent`, но на провод она не попадает (в пире нет ни одного не-SYN кадра с MAC гостя). То есть `bytes_sent == bytes_queued` тоже не доказывает доставку каждого кадра
  (в продукте кадры короче `MIN_TX_FRAME` отсекаются до очереди, это лишь иллюстрация). Доставку, как и прежде, доказывает захват пира.
- Кадр 9000 байт отвергается так же, как в споке 2B для `pcap_sendpacket` (код 20), но теперь с побочным эффектом: префикс уже ушёл.
- Не воспроизведено: частичный возврат с ненулевым значением (в потере линка r13 `bytes_sent == bytes_queued` во всех вызовах). Другие причины частичного transmit на этом стенде не найдены.

## Задержка Stop (`live_sendqueue_stop_latency`, n = 64)

TX-поток шлёт пачки по 64 SYN (потолок 100k pps), RX-поток крутит `recv` с дедлайном 42 мс (Hybrid) на втором handle; стоп-флаг ставится через 20-300 мс
(SHA-256 от номера раунда и часов). Время от флага до выхода TX и до `join` обоих потоков, мкс:

| Прогон | раундов | transmit | TX: p50 / p95 / max | RX: p50 / max | join: p50 / p95 / max | самый долгий transmit раунда: p50 / p99 / max |
|---|---|---|---|---|---|---|
| r11 idle | 60 | 3 664 | 1 373 / 3 430 / 5 352 | 51 / 2 291 | 1 713 / 3 529 / 5 438 | 6 369 / 8 577 / 9 105 |
| r12 flood | 60 | 3 113 | 1 408 / 5 086 / 6 290 | 41 / 8 244 | 1 884 / 5 551 / 9 709 | 7 033 / 19 542 / **44 421** |
| r14 flood | 200 | 10 318 | 1 491 / 5 738 / 7 734 | 42 / 3 470 | 1 796 / 5 822 / 7 842 | 6 438 / 10 527 / 13 535 |

- Максимум по всем 320 раундам: TX выходит через ≤ **7.73 мс** после флага, оба потока присоединены за ≤ **9.71 мс** (предел 1 с, запас ~100×). Задержка TX не превышает самый долгий transmit раунда
  (`worst_tx_excess_over_slowest_transmit_us = 0` в каждом прогоне): Stop ждёт не больше одного transmit.
- `short_transmits = 0`, ошибок RX нет. Ожидание брифа «≈ 100 мс» не подтверждается: RX handle видит собственный TX-трафик и поток, поэтому `recv` почти всегда возвращается сразу, а дедлайн 42 мс на пустом канале не вовлечён; худший случай RX это ещё одно ожидание до 42 мс, так что верхняя граница join остаётся ≤ ~50 мс + transmit.
- **Выброс**: в r12 один transmit из 64 кадров занял **44.4 мс**, больше `IO_BUDGET` 42 мс (при конкурирующем RX-потоке и потоке мусора). В r14 на 10 318 transmit максимум 13.5 мс, в r11 9.1 мс. Один выброс на 13 431 transmit с потоком мусора (r12 + r14), на 17 095 transmit с конкурирующим RX всего (r11 + r12 + r14); см. «Риски».
- Одновременный RX-поток замедляет transmit (n = 64: p50 раунда 6.4-7.0 мс против 3.5 мс без RX в r01 idle и 1.7 мс в быстром режиме).

## Потеря линка (`live_sendqueue_linkdown`, r13; информационно)

`rmasscan-lab peer linkloss --down-after 2.0 --hold-max 10`: QMP `set_link` down через 2 с после первого SYN гостя, up через 10.01 с; тест слал 2 344 пачки по 64 кадра (150 016 кадров, 5k pps) 30 с.

- Состояние NIC гостя по `nic-status.txt` (каждые 500 мс): Up → Disconnected на 20 отсчётов (~10 с) → Up.
- Все 2 344 transmit вернули `bytes_sent == bytes_queued` (`sent != queued` ноль), длительности нормальные: p50 1.96 мс, max 10.6 мс (внутри окна down макс 6.55 мс). Нет ошибки, нет зависания, нет частичного возврата.
- Пир получил 97 408 из 150 016 кадров. Пропали 52 608 (822 вызова целиком; **ни одного частично доставленного вызова**), от +0.016 с после down до +0.499 с после up: линк возвращается за ~0.5 с.
  Пропавшие кадры считались «отправленными»: sendqueue при потере линка это такая же «чёрная дыра», как `pcap_sendpacket` в споке 2B (rc 0).
- Для части B `linkloss` приёмки: `tx_sent` будет больше SYN на проводе; правило `tx_sent == SYN на проводе` для этого случая должно трактоваться как в прежней части B (потеря на линке, не TX-ошибка).

## Что узнали

1. `pcap_sendqueue_transmit` синхронен и не отменяем: n = 64 занимает 1.7-6.3 мс (по режиму), 256 → 6.6-22 мс, 1024 → 27-82 мс, 4096 → 102-320 мс.
   Стоимость почти линейна по кадрам (~27 мкс на кадр в быстром режиме, ~55 мкс в медленном; 125-140 мкс для одного кадра), поэтому выигрыш пачки по сравнению с `pcap_sendpacket` 2.5-5×, но не на порядок.
2. Потолок VM с sendqueue 16-37k pps (против 6.4-7.5k у одиночного пути), для 100k pps на этой VM недостижимо при любом n. Это честный OPEN для части C, не провал продукта.
3. Тайминг VM бимодален (17k/37k pps) и не привязан к условию; одиночный прогон ряда не надёжен, нужны повторы.
4. Ошибка записи в очереди: префикс уходит, остальное нет, число возвращается 0. Точного учёта нет.
5. `bytes_sent == bytes_queued` не доказывает доставку (runt-запись принята и не доставлена; потеря линка).
6. `clear()` безопасен; handles и рабочий набор стабильны.
7. Stop укладывается с запасом ~100×.

## Рекомендации задаче 4

- `TX_BATCH_FRAMES = 64`, байты очереди `64 × (16 + 1518)`; `MAX_TX_BATCH` движка не ограничивает (4096 больше).
- Частичный transmit: **STOP точного учёта префикса**. `PREFIX_ACCOUNTING` выключить: `bytes_sent == queued_bytes` → все `Sent`; любое другое значение, включая 0, → вся пачка `Uncertain`
  → `Failed(TxUncertain)` без checkpoint и без повтора. Нельзя трактовать `bytes_sent == 0` как «ничего не ушло»: до k кадров могли дойти до пира.
  Ранее данные: правило «не на границе → всё Uncertain» остаётся и становится единственным; ветку «граница записи → префикс Sent» оставить как код за переключателем (NOT RUN: живьём не воспроизведена), в приёмке не заявлять.
- `clear()` между пачками; destroy/alloc не нужен (решение 7 плана остаётся).
- `tx_over_budget` приёмки: ждать единичных выбросов (44.4 мс на 13 431 transmit при RX-конкуренции и потоке мусора); см. «Риски».
- Stop: достаточно «`halt` перед каждой пачкой»; измеренная задержка ≤ 7.73 мс.

## Риски и ограничения

- n = 64 тоже не защищён абсолютно: в r12 один transmit 44.4 мс > `IO_BUDGET` 42 мс. Приёмка с `tx_over_budget = 0` может иногда упасть на выбросе VM; если требуется нулевое значение
  на 100% прогонов, нужен меньший n (16: p99.9 ≤ 2.7 мс) либо пересмотр бюджета отдельным решением (в этом отчёте лимиты не ослаблялись).
- Режимы 17k/37k pps дают разный pps приёмки части C на VM; медиана ±20% (gate) может быть нестабильной между режимами.
- RX-поток в замерах timing не работал (замер с RX только в r11/r12/r14 на n = 64); в продукте он параллелен и замедляет transmit (см. Stop).
- p99.9 по 200 вызовам = max; правило и в брифе задано на 200. Дополнительные 1000 вызовов (r07/r08) подтвердили, что хвост 256 лежит на лимите.
- Результаты относятся к debug/test-профилю «optimized + debuginfo» проекта, Npcap 1.90, e1000e, одному гостю; физический NIC NOT RUN.
- Полные pcap больших прогонов хранятся только на `home-pc` (`~/winvm/sq-ev/`); в репозитории sha256, размер и excerpt.
