### 3.1. Что проверено в `linux-banners-r1`

Стенд: запечатанный стенд autodetect (`198.18.0.0/24`, без uplink) с `net.ipv4.icmp_ratemask=0` в netns пира (стенд
протоколов). Argv обоих кейсов: `198.18.0.2-198.18.0.5 -sU -p53,123,137,161,500,1900,5683,11211,16464 <--banners|--rawudp>
<-oB output.bin|-oL output.txt> --seed 1 --rate 100 --wait 3 --source-port 40000 --retries 0`; на каждый документ шаг
rmasscan и шаг оракула с одним argv, у каждого свой захват пира и перезапущенный ответчик (8 шагов).

Ответчик (`capture responder --udp-answer banners`, `banners_verify::scenario_reply`): по сокету на адрес пира и порт,
на каждую датаграмму один ответ сценария этого адреса и порта, идентификатор зонда скопирован в ответ (DNS и NetBIOS id,

и `retL` ZeroAccess (адреса `198.18.0.2`–`.4`), чтобы текст баннера не назвал MAC и адреса вне стенда. Перед окном вывод

## 11. Замечания

- Код лаборатории и прежние каталоги несут имена хостов в двух местах, которые этот подэтап не трогал: имя файла
  хэшей pcap прогона Windows, заданное `windows-suite` (в нём прежний псевдоним хоста VM) и причина `#[ignore]` в `rmasscan-core/tests/offline_gen.rs:36`; оба попадают в
  evidence. Переименование — отдельная правка кода лаборатории и теста (с ней сменятся имена файлов будущих каталогов Windows).
- Граница очереди движка в записях, а не байтах (журнал задачи 6): окно её не нагружает; бюджет в байтах — до 4b.
- `privacy-scan` теперь пропускает собственные кадры NBNS стенда баннеров (точное сравнение байтов, И5 спеки); любой
  другой кадр NBNS остаётся попаданием, строка итога называет число пропущенных (64 в `linux-banners-r1`, 0 в остальных).
- Ответы сценариев взяты из эталонов задач 4–5 через `include_bytes!`: правка эталона меняет ответ стенда, а тест
  `the_replies_are_the_c_goldens_with_the_probes_cookie_or_a_spoiled_one` закрепляет связь.

## 12. Privacy

`rmasscan-lab privacy-scan` (сборка C на Mac) прогнан по копии каждого каталога окон, по `fuzz-udp-r1/`, по `verification/` и по
всему каталогу сырых данных (с `README.md`) с `--forbid` для восьми идентифицирующих имён длиной от 4 байт, известных оператору
(имена хоста и компьютера Mac, учётная запись Mac и две её части, имена хоста стенда Linux и хоста VM, прежнее имя профиля
Windows на хосте VM): **0 совпадений** везде (rc 0), положительный контроль (файл с токеном № 4) даёт попадание (rc 1), токен короче
4 байт отклоняется (rc 2, токен не печатается). Кадры NBNS окна `banners` (64: 8 шагов × 4 зонда и 4 ответа) `privacy-scan`
считает собственными кадрами стенда по точному сравнению байтов (И5 спеки); других кадров mDNS, LLMNR, NBNS и ICMPv6 с именами
нет ни в одном захвате. Пословный `grep -ralwE` по всем именам хостов и учётных записей, в том числе двух- и трёхсимвольным, и
по `_tcp`/`_udp` `.local`: 0 файлов. `grep -ral` по путям домашних каталогов, префиксу домашней сети, корню scratch агента и
временных каталогов macOS: 0 файлов. Имена хостов в именах файлов `verification/` заменены ролями (`linux-stand-*`,
`vm-host-*`), в тексте отчёта и README сырых данных хосты названы по ролям. В evidence остаются две старые строки самого
репозитория: имя файла хэшей pcap прогона Windows, которое задаёт `windows-suite` (с прежним псевдонимом хоста VM), и причина `#[ignore]` теста
`offline_generation_meets_80pct_of_oracle` (`rmasscan-core/tests/offline_gen.rs:36`), которую печатают логи тестов; обе уже в
публичном коде (раздел 11). Вывод: `verification/privacy-scan.txt`.
