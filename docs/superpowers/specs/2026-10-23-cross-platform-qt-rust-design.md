## 0. Текущее состояние и перечень возможностей

Статус привязан к commit `c31ae16` ветки `feat/rmasscan-stage2b-linux`
(2026-10-24). Он не распространяется на более поздние коммиты и не заменяет
свежую проверку. Исторические отчёты в `docs/experiments/` остаются
историческими: каждый описывает базу, указанную в его первых строках.

### 0.1. Контракты engine (реализованы)

Реализовано в `364ee49` (RX integrity) и `c31ae16` (TX stall); ссылки на
коммиты это основание, а не обещание для других веток.

| Область | Контракт |
| --- | --- |
| RX health | `Rx::health(timeout) -> Result<RxHealth, IoError>`: обязательный метод; `RxHealth { kernel_drops: Option<u64> }` кумулятивно с начала попытки; `None` означает «измерить нельзя» и никогда не становится нулём |
| Проверка | Не реже раза в 250 мс по часам engine и обязательная финальная проверка перед исходом |
| Исходы | `FailReason::RxLoss { kernel_drops }` при drops > 0, `RxStatsUnavailable` при `None`, `RxError(String)` при ошибке запроса статистики; ранее сохранённый ноль не подменяет ошибку. Принятые результаты остаются доступными; checkpoint не создаётся |
| Outcome | `Outcome.rx_health: RxHealth` (не `Option`): последнее успешно измеренное состояние. Если запрос статистики завершился ошибкой, поле сбрасывается в `RxHealth { kernel_drops: None }`: ранее измеренный `Some(0)` не сохраняется и не подменяет ошибку. `kernel_drops: None` также, если измерения не было или статистики нет |
| Приоритет | Первый отказ сохраняется. `Completed`, `Stopped`, `Paused` возможны только при подтверждённом `Some(0)`, в том числе при одновременном Stop |
| Смысл Completed | Задание завершено, статистика доступна, kernel drops не наблюдались. Это не «найдены все открытые порты сети»: ноль drops не доказывает отсутствие потерь в сети или у удалённого хоста, а ненулевое значение консервативно (может включать посторонние кадры) |
| TX stall | `EngineOptions::tx_stall_timeout`, по умолчанию `DEFAULT_TX_STALL_TIMEOUT` = 10 с; ноль отвергается (`StartError::InvalidOptions`). Окно идёт от первой попытки кадра, вернувшей `WouldBlockUnsent`, и сбрасывается только после `Sent`; throttle-сон между кадрами не считается. Итог `FailReason::TxStalled { idle_millis }`, курсор не продвинут, checkpoint не создаётся |
| Прочее | Только `Sent` продвигает курсор; `Uncertain` даёт `Failed` без повтора и checkpoint. Один вызов адаптера ≤50 мс, Stop ≤1 с |

Эти правила не заменяют отдельную проверку truncation, capture filters и
поддерживаемых типов канала.

**Типизированные события engine** (`rmasscan-engine`, `src/events.rs`) заменяют
для встроенного сканера argv, разбор stdout/stderr, `paused.conf` и сигналы
процесса. Потребитель получает `Event::Started { range }`,
`Event::Progress(Progress)`, `Event::Results { replies }`,
`Event::CheckpointReady { next_index }` (только после чистой паузы) и последнее
`Event::Finished { reason }`; итог запуска это `Outcome { reason, progress,
rx_health }`, причины `Reason::{Completed, Stopped, Paused, Failed(FailReason)}`.
Тип `Checkpoint` и `CHECKPOINT_FORMAT_VERSION` определены в
`rmasscan-engine/src/checkpoint.rs`. `Reason::Paused` и `CheckpointReady` не
означают сохранённую паузу: её подтверждает Studio после durable commit (ACK, §6).
Это реализованный интерфейс; набросок API в §10 спеки порта исторический и с
кодом не совпадает (`RawAdapter`, `PortStatus` и т. п. там не существуют).

### Инженерные решения и проверяемые гипотезы

Это инженерные настройки, а не дополнительные ответы пользователя. Их можно
уточнять по измерениям, сохраняя согласованные требования. Экспериментальные
механизмы принимаются только после проверки.

| Область | Предложение автора |
| --- | --- |
| SQLite | WAL + synchronous=FULL; batch commit каждые 250 мс или 1000 результатов; ACK checkpoint только после commit |
| UI delivery | Пакеты каждые 50 мс или 1000 изменений; очередь 4 MiB сериализованных событий; overhead измеряется отдельно |
| u64 | Decimal TEXT для seed/index в SQLite, строки на границе UI; допустимость индекса проверяется отдельно |
| Orphan test | Проверяемый предел 2 с после forced death runner; не заявленная гарантия до эксперимента |
| UI-прототипы | A1 Slint на Mac: 1–2 рабочих дня и резерв 1 день; A2 после A1; истечение бюджета даёт отчёт, не автоматический FAIL |
| Build/UI | Будущая команда cargo xtask build; английский интерфейс как в v0.3 |
| Импорт | UUID + источник; повтор пропускается, изменившийся уже импортированный объект даёт конфликт, без перезаписи новой истории |
| Личная v1 | Модель угроз §5.3 исключает компрометацию учётной записи владельца; сертификаты и постоянные службы не предполагаются |

**Обязательно для v1:** паритет, три ОС, согласованные метрики, один экземпляр
на канонический каталог данных, базовый version handshake, остановка при
обрыве/падении runner, долговечный checkpoint и корректный статус после сбоя.
Сон и смена сети требуют базового обнаружения/сверки и остановки без автозапуска;
это не обещание универсальной интеграции с каждым VPN-клиентом.

**Укрепление на потом:** дополнительные adversarial-тесты алиасов путей сверх
обычной каноникализации, расширенная матрица сна/VPN, стресс-тест на 1M строк,
автоматическое согласование разных версий протокола. Эти проверки не блокируют
выбор UI и личную v1; 100k и весь паритет остаются обязательными.

## 2. Исходное состояние и границы переноса

Репозиторий: https://github.com/disclaimer8/masscan-studio.
Локально: `/Users/denyskolomiiets/masscan-studio`, ветка `main`, исходный коммит
`b02dd2968563bd4af952748272f2d7bb92568281`.

Текущая v0.3 написана на Swift/SwiftUI для macOS 14+: `ScanCore`, `ScanHelper`,
`MasscanStudio`. Darwin, AppKit, Network, dnssd и AppleScript делают перенос
существенной переработкой, а не сменой цели сборки. masscan и Nmap — внешние
программы, скорость сетевого сканирования определяет masscan.

Зашитые сегодня пути: `/opt/homebrew/bin`, `/usr/local/bin`, `/private/tmp`.
Текущий helper получает права через osascript, связывается с UI по loopback TCP,
получает token через argv, копирует masscan на сеанс и создаёт каталог на попытку.
История/профили — JSON в `~/Library/Application Support/Masscan Studio/`.
Чтением при прошлом ревью подтверждены 2 сессии и 971 результат; это не нагрузочный
тест. Реальную историю не помещаем в fixtures или Git.

`docs/VERIFICATION.md` фиксирует проверки masscan 1.3.2 и Nmap 7.992, Swift-тесты,
helper/`--echo` и Nmap на локальном fixture. Там **не подтверждены агентом**
настоящий привилегированный скан и живой pause/resume на macOS. Текущий код служит
эталоном проверенного поведения, а живая пауза требует отдельной проверки.

Первая версия сохраняет функции v0.3 на трёх целевых ОС. Не входит: IPv6/UDP,
удалённый сканер, мобильная/веб-версия, облачная синхронизация, телеметрия,
удалённые crash reports, автообновления, публичные установщики и публичная подпись.
Нет постоянного привилегированного демона/Windows service, изменений firewall,
поля произвольной CLI-команды и автоматического сканирования. Нет молчаливой
установки драйверов, capabilities, групп, антивирусных исключений или зависимостей.
Flatpak/Snap и AppImage не входят в первую версию; это ограничение объёма.

## 3. Архитектура, независимая от UI

```text
                 Slint + адаптер
                      |
        Rust application/core (обычные права)
         |             |                 |
      SQLite       DNS / Nmap       typed local IPC
                                         |
                           Rust runner (без Qt/Slint)
                                         |
                         rmasscan engine (библиотека,
                           потоки внутри runner)
```

Ядро проверяет конфигурацию, получает типизированные результаты/прогресс,
управляет жизненным циклом, хранит данные и экспортирует их. UI показывает
модель и отправляет типизированные действия; не выполняет SQL, сканы, DNS,
парсинг больших данных или запись истории в графическом потоке.

Runner — отдельный небольшой Rust-бинарник без GUI-фреймворка и загрузки UI-плагинов.
Общий независимый crate валидации используется ядром и runner; проверка проводится
с обеих сторон. API runner не принимает shell-команду, произвольный executable,
путь файла результатов или команды для Nmap. Nmap запускается ядром без повышения.

Выбранный Slint: Rust API и .slint, backend/style без Qt. Готовый StandardTableView
содержит текстовые ячейки, поэтому кликабельные ячейки и выбор требуют своего
компонента. Проверяется реальная стоимость этой реализации, а не Hello World.
Файловые диалоги/открытие URL подключаются через платформенные адаптеры.

## 5. Runner, доверие и время жизни

### 5.1. Сессионная модель

> **Ред. 8 (история):** установка и проверка копии masscan в доверенном каталоге (последний абзац этого раздела). **Ред. 8 (норма):** доверенной установке подлежит сам runner; отдельной копии masscan нет. Перечисленное в «Ред. 8 (история)» это исторический Swift-эталон и не действует для встроенного rmasscan; остальной текст раздела остаётся в силе.

Сохраняется модель v0.3: один runner на сеанс приложения и последовательные
попытки сканирования. UI не работает от root/administrator и не собирает пароль.
Lock доступен в idle, как в Swift; во время скана пользователь сначала делает
Pause/Stop. Выход приложения инициирует остановку и отзыв сеанса. После смерти
runner старую авторизацию не восстанавливаем; следующий скан создаёт новый сеанс.

Кандидаты повышения прав: macOS — osascript `do shell script … with administrator
privileges` по существующей схеме; Windows — ShellExecuteExW с `runas`;
Ubuntu — pkexec для абсолютного пути runner с системным polkit-agent.
Они проверяются в новой связке; существование схемы osascript в Swift не является
доказательством живого привилегированного прогона. Отмена/отсутствие агента дают
понятную ошибку без fallback к ручному сбору пароля. Постоянная служба не нужна.
Минимально достаточные права предпочтительны полному root, но их достаточность
подтверждается на выбранной сборке masscan. Nmap и validation всегда отдельно.

Решение автора спеки: до полного runner подготовить по ОС запись о доверенной
установке helper/scanner и необходимых библиотеках: защищённый от пользовательской
записи каталог, владелец/ACL, проверка бинарника, явное обновление/удаление.
Для личной v1 кандидат macOS — `/Library/PrivilegedHelperTools/MasscanStudio/`
с root-owned runner и без регистрации daemon; Linux —
`/usr/local/libexec/masscan-studio/`; Windows — `Program Files\Masscan Studio\`.
Сам runner и родительские каталоги защищены от записи обычным пользователем.
Установка/обновление/удаление выполняются явно один раз с административными правами;
bootstrap не выполняет исходник из build-каталога. Обычный build-каталог
не становится доверенным только из-за запроса пароля. Разовая административная
установка файлов не равна постоянной службе и допускается в инструкции личной
сборки; сейчас она не выполняется. Подпись/сертификат не предполагаются доступными.

На macOS личная установка явно помещает проверенную копию masscan в тот же
root-owned каталог `/Library/PrivilegedHelperTools/MasscanStudio/`; зависимости
также должны удовлетворять требованиям доверенной установки. Пользовательский
Homebrew-каталог не является источником для непосредственного root-запуска или
автоматического обновления этой копии. Это осознанно строже v0.3, где runner
копирует resolved-бинарник из Homebrew уже после повышения прав. Обнаружение
Homebrew-бинарника для настройки/validation не означает доверия к нему под root.

### 5.2. Инварианты выполнения

> **Ред. 8 (история):** пункты «Запуск только проверенного masscan», «Копия masscan», «Каждый запуск/resume имеет отдельный рабочий каталог» (чтение `paused.conf`) и «Unix stop: SIGINT…» с Windows console event. **Ред. 8 (норма):** остановка встроенного engine это `Stop` (≤1 с) и `Pause` с `CheckpointReady`, `paused.conf` не читается (§0.1); остальные инварианты (один активный скан, повторная валидация в runner, остановка при разрыве IPC, forced termination даёт Interrupted/Failed, а не Paused) действуют. Перечисленное в «Ред. 8 (история)» это исторический Swift-эталон и не действует для встроенного rmasscan; остальной текст раздела остаётся в силе.

- Повторная валидация в runner; один активный scan, новый `run` во время него отклоняется.
- Неизвестная команда/некорректный кадр отзывает сеанс и останавливает его скан.
- Разрыв IPC при живом runner запускает остановку. Смерть runner покрывается отдельно (§5.4).
- Авторизация UI: до 180 секунд; кадр команды ≤131072 байт — контракты Swift.
  Handshake после запуска: 10 секунд — новое решение автора спеки, не таймаут из Swift.
- Запуск только проверенного masscan. Зафиксировать его версию и SHA-256 на сеанс;
  доверенный исходный файл/зависимости нельзя подменить между проверкой и запуском.
- Копия masscan в приватном каталоге сеанса, как в Swift, — исходный механизм
  фиксации, но не доказательство доверия к исходному файлу. На других ОС допустим
  эквивалент с защищённым immutable-файлом; file capabilities и DLL-зависимости
  при копировании проверяются отдельно. Обоснование эквивалента входит в отчёт.
- Каждый запуск/resume имеет отдельный рабочий каталог; `paused.conf` читается
  только после завершения именно этой попытки. Каталоги не переиспользуются.
- Allowlist окружения и абсолютные пути. На Unix исходно PATH и LC_ALL=C;
  Windows сохраняет только необходимые системные переменные по явному списку.
  Не наследовать переменные загрузчика или искать DLL в пользовательском cwd.
- Runner пишет только свои приватные временные файлы. SQLite/экспорт пишет ядро
  без повышенных прав. Root не пишет в пользовательское хранилище.
- Unix stop: SIGINT, после 8 с SIGTERM, после 12 с от исходного stop SIGKILL.
  Windows: проверенный graceful console event и принудительный выход в том же
  общем 12-секундном бюджете; не выдумывать эквивалент SIGTERM.
- Forced termination даёт Interrupted/Failed, а не Paused; остаток временных
  каталогов после crash очищается только безопасным владельцем без следования
  пользовательским symlink. Очистка не выполняет найденные конфигурации.

### 5.3. IPC и смена версии

**Модель угроз личной v1:** защищаемся от других непривилегированных локальных
пользователей, подключения старых/чужих сеансов, replay, PID reuse и подмены
endpoint. Доверяем ОС, администратору, установленному runner/scanner и владельцу
сеанса. Вредоносный код с правами владельца, внедрение в UI, кража его файлов/
handle, а также компрометация root/administrator вне этой модели. Мы подтверждаем
учётную запись и конкретный сеанс, а не доказываем неподменяемую идентичность
неподписанного UI. При публичном выпуске модель пересматривается отдельно.

Токен не передаётся через argv/env. Имя endpoint, PID/UID UI и session ID не
являются секретами и могут передаваться как аргументы; сами по себе они не дают
доступа. Исходный TCP/argv-token заменяется следующим bootstrap-кандидатом:

- Unix: UI создаёт уникальный domain socket в каталоге 0700. Runner проверяет
  владельца/тип/права каталога и socket без следования подставленным symlink,
  затем peer UID/PID UI: SO_PEERCRED на Linux, getpeereid + LOCAL_PEERPID на macOS.
  UI проверяет peer UID (root при повышении) и процесс по доверенному пути runner.
  PID связывается с живым процессом/временем старта и текущим launch, а не только
  с сохранённым числом. Повторный endpoint после закрытия сеанса не принимается.
- Windows: UI создаёт уникальный named pipe с DACL для владельца и только
  необходимых системных/elevated principals, FILE_FLAG_FIRST_PIPE_INSTANCE и
  PIPE_REJECT_REMOTE_CLIENTS. ShellExecuteExW `runas` вызывается с
  SEE_MASK_NOCLOSEPROCESS; без возвращённого handle запуск не считается связанным.
  UI сравнивает GetNamedPipeClientProcessId с процессом из удерживаемого handle.
  Runner проверяет GetNamedPipeServerProcessId, учётную запись/время создания UI
  и удерживает открытый process handle до конца сеанса. Отдельно проверяется
  UAC с вводом другой административной учётки: DACL не ослабляется до Everyone.

Конкретная проверка process identity после osascript/pkexec, доступность API
и поведение UAC проверяются при bootstrap-тесте. stdin после UAC не считается
унаследованным каналом. Ошибка peer/process/endpoint-проверки закрывает канал
до run. Сценарии старого сеанса и повторного PID входят в обязательные тесты,
попытки внедрения вредоносного кода того же пользователя не являются gate v1.

Handshake содержит protocol version, build ID, session ID и capabilities.
Несовместимость — отказ до скана, без silent downgrade. Каждая попытка имеет
scan_id и attempt_id; чужие/старые события не изменяют другую сессию.
При ручном обновлении закрывается старая авторизация. Новый UI не принимает
поднятый ранее runner другой версии. Несовместимый helper даёт понятную диагностику.

### 5.4. Смерть runner: обязательный эксперимент

> **Ред. 8 (история):** формулировка «не допускается оставшийся без управления привилегированный masscan» и управление дочерним процессом masscan. **Ред. 8 (норма):** эксперимент остаётся обязательным: сканер встроен в runner и умирает вместе с ним, поэтому проверяется, что runner завершается при смерти/разрыве IPC и не остаётся привилегированного процесса; пригодность кандидатов ниже (Job Object, SIGPIPE, PDEATHSIG) для этой цели определяет эксперимент. Перечисленное в «Ред. 8 (история)» это исторический Swift-эталон и не действует для встроенного rmasscan; остальной текст раздела остаётся в силе.

Drop/destructor и обработчик разрыва канала не работают после смерти самого
runner. Не допускается оставшийся без управления привилегированный masscan.

| ОС | Кандидат | Что необходимо доказать |
| --- | --- | --- |
| Windows | Job Object, KILL_ON_JOB_CLOSE; child suspended до назначения job | Последний handle только у контроллера, без наследования и breakaway; при ошибке назначения скан не стартует |
| macOS/Linux | Приватный stderr pipe и SIGPIPE при смерти единственного reader-runner | SIG_DFL и незаблокированный SIGPIPE у scanner; read-end не утекает; status не отключён; измерена задержка во всех фазах |
| Linux, дополнительный вариант | PR_SET_PDEATHSIG до exec и проверка гонки смерти родителя | Сигнал не потерян при credentials/file capabilities; учтён thread, породивший child |

В проверенном локальном upstream нет обработки SIGPIPE/SIG_IGN; status_print
пишет stderr и делает fflush как во время передачи, так и drain. POSIX write
в pipe без readers вызывает SIGPIPE [S13]. Rust std по умолчанию восстанавливает
SIG_DFL перед child exec [S14], но disposition, mask, build flags и fd-наследование
нужно проверить у фактического child. Нынешний Swift-runner сам игнорирует SIGPIPE;
переносить это состояние в scanner нельзя.

Read-end принадлежит только runner, закрывается во всех child/launcher, не
передаётся UI/логгеру; данные reader пересылает UI сообщениями. Запрещены режимы,
отключающие status, и перенаправление stderr в обычный файл. Runner продолжает
читать pipe даже при медленном UI. SIGPIPE завершает scanner как Interrupted,
не создавая обещания checkpoint; file capabilities не требуют PDEATHSIG для
этого кандидата, но всю выбранную цепочку запуска всё равно проверяем.

**Ограничение:** SIGPIPE действует только при следующей записи. Код статусного
цикла не доказывает предел 2 с до первого status, при зависании, инициализации
адаптера или долгом блокирующем вызове. Проверить запуск, активный scan, drain,
паузу и доставку checkpoint, включая forced death reader и утечки fd, сначала
с fake scanner, затем с выбранным masscan. Если scanner остаётся живым дольше
2 с наблюдения, кандидат не прошёл в данной фазе; нужен дополнительный механизм
или отдельное решение о контракте, а не молчаливое исключение фазы из теста.
PR_SET_PDEATHSIG как дополнительный вариант Linux имеет ограничения при
credentials/file capabilities [S6]. Постоянный daemon не добавляется.

Отдельно протоколируются два сценария: смерть runner при работающем выбранном
механизме защиты и одновременная гибель всех наших управляющих процессов
(UI/runner/контроллер, если он потребуется), но без прямого сигнала scanner.
Первый проверяет предел 2 с; второй — устойчивость механизма и фактический предел
каждой ОС. Отсутствие аналога Job Object само по себе не означает FAIL: оценивается
поведение выбранного механизма, включая stderr/SIGPIPE. Если второй сценарий
оставляет scanner живым, результат не скрывается за PASS первого: до реального
использования требуется отдельное решение пользователя об ограничении гарантии
или иной механизм. Наличие собственного supervisor само по себе не доказательство.

## 6. Pause/Resume и передача checkpoint

> **Ред. 8 (история):** неявное чтение `/etc/masscan/masscan.conf` (в коде rmasscan такого чтения нет), чтение `paused.conf` из cwd попытки, `--resume-index` в argv, Windows console event (AttachConsole/GenerateConsoleCtrlEvent). **Ред. 8 (норма):** checkpoint приходит событием `CheckpointReady { next_index }` и типом `Checkpoint`; его сохраняют в SQLite и подтверждают ACK по шагам 2–5 ниже; привязка к исходному заданию и seed, decimal TEXT для `seed`/`resumeIndex`, граничные проверки u64 и правило «не выпускаем Windows без функции» действуют. Перечисленное в «Ред. 8 (история)» это исторический Swift-эталон и не действует для встроенного rmasscan; остальной текст раздела остаётся в силе.

Checkpoint принадлежит неизменяемой конфигурации задания: нормализованные цели,
порты, exclusions, seed, параметры порядка обхода и совместимая сборка scanner.
Resume создаёт новую попытку того же задания, не новый seed. Изменение сети/
интерфейса требует проверки и явного действия пользователя, не автоматического старта.

В проверенном upstream на **не-Windows** системах (Linux и macOS), если нет
`--readscan`, до argv читается `/etc/masscan/masscan.conf` при его наличии
(`src/main.c:1615–1640`). Поэтому одинаковые argv и seed недостаточны.
Идентичность задания включает наличие/отсутствие этого файла, снимок его содержимого
и SHA-256, а также содержимое/hash реально используемых внешних файлов конфигурации,
включая exclusions. Снимки хранятся приватно вместе с заданием; эффективная
конфигурация после defaults и argv сверяется через `--echo` без scan packets.
Явные argv могут переопределить defaults, но не считаются способом отменить все
неявные настройки. Системные exclusions не удаляются для удобства Resume.

Перед каждой попыткой проверяются конфигурация и зависимости; изменение относительно
checkpoint блокирует Resume с объяснением. Сохранение снимка не заставляет masscan
читать именно его: способ исключить подмену/изменение между проверкой и чтением
scanner должен быть подтверждён экспериментом. До этого воспроизводимость не
объявляется доказанной. Системный файл не переписывается приложением. Эта проверка
относится к Unix-прогонам и не объясняет сбой прототипа B на Windows, где указанная
ветка upstream исключена при сборке.

Swift уже передаёт индекс событием `checkpoint` как десятичный текст, UI читает
UInt64 и сохраняет config при событии выхода. Новый протокол дополняет это:

1. Runner после graceful exit читает ограниченный checkpoint из cwd попытки,
   проверяет формат, индекс и принадлежность попытке; не исполняет raw paused.conf.
2. Отправляет scan_id/attempt_id, точный индекс и идентичность конфигурации/сборки.
3. Rust-ядро сохраняет финальные результаты и checkpoint транзакционно; только
   после успешного commit отправляет ACK и показывает Paused/Resume.
4. Повтор события идемпотентен. После ACK runner очищает каталог. При потере ACK
   живой runner хранит pending-событие до закрытия сеанса, без вечного daemon.
5. Если до commit умерли UI/runner, checkpoint может потеряться: после рестарта
   Interrupted без ложного Resume. После commit новый UI восстанавливает
   checkpoint из SQLite, запрашивает новый сеанс и не нуждается в старом root-файле.

`seed` и `resumeIndex` — u64/Option<u64> в Rust. В QML/Slint они не входят как
числа: только десятичные строки, если UI вообще нужны эти поля. Учитываются
32-битный UI int и потеря точности JavaScript Number выше 2^53. SQLite INTEGER
знаковый 64-битный, поэтому решение автора: эти два поля хранятся как проверенный
канонический decimal TEXT, не через REAL/double. JSON истории разбирает Rust.

Граничные проверки представления: 2^31, 2^53±1, `18446744073709551614`, u64::MAX,
null, отрицательные и overflow. Большое значение из Swift-теста — **тест парсера,
а не допустимый индекс настоящего задания**. До запуска отдельно проверяется
допустимость resume-index для конфигурации/сборки; невозможный индекс сохраняется
для диагностики импорта, но не отправляется masscan. Не принимать 2^48 за
универсальный предел всех режимов upstream: retries/другие режимы влияют на обход.

Windows требует отдельного доказательства. Upstream в проверенном клоне ловит
SIGINT через CRT signal(); CTRL_BREAK не считается его эквивалентом.
CTRL_C_EVENT нельзя адресовать отдельной process group, а CREATE_NEW_PROCESS_GROUP
меняет обработку Ctrl+C [S4]. Кандидат — изолированная консоль scanner и контроллер
AttachConsole/GenerateConsoleCtrlEvent; конкретная последовательность проверяется,
включая UAC и защиту контроллера/чужих процессов от события.

При провале паузы не заменяем её Kill, не выпускаем Windows без функции и не
объявляем весь перенос завершённым. Доступные диагностические сборки других ОС
могут тестироваться, но это не готовая первая версия для трёх платформ.

## 7. SQLite, импорт и восстановление

SQLite хранит результаты, задания/попытки, профили, inspection, настройки и версию
схемы. Один Rust writer, параметризованный SQL, индексированный выбор данных,
без полного копирования таблицы на каждое событие. Решение автора: WAL +
synchronous=FULL; исходный batch commit — каждые 250 мс или 1000 результатов.
Параметры batch можно менять по измерениям, не ослабляя подтверждение checkpoint.
WAL не спасает незакоммиченные данные: различать received/displayed/committed
и не обещать нулевую потерю последнего batch при crash [S7].

Каталог данных отдельный от Swift. На Unix 0700, файлы БД/WAL/SHM/backup 0600,
на Windows ограниченный ACL владельца. Это права доступа, не шифрование.
Схема версионируется; миграция транзакционна, перед изменением — пригодная для
восстановления копия. Backup живой WAL-БД не выполняется простым копированием
одного файла; использовать механизм SQLite backup/согласованный snapshot.

OS-backed single-instance lock берётся до открытия хранилища/runner для пары
пользователь + канонический каталог данных. Второй запуск активирует окно либо
сообщает о занятом экземпляре, не запускает скан. Lock не снимается только по
«старому PID»; проверить crash release и алиасы пути. SQLite-lock не заменяет
владение приложением. Swift не знает нового lock: одновременная запись в его
файлы запрещена, оригиналы используются только для чтения при импорте.

Импорт запускается вручную **только на macOS** из sessions.json/profiles.json.
Пользователю предлагается закрыть Swift перед импортом; проверяется стабильный
snapshot источника. Валидация обоих файлов целиком предшествует транзакции.
Ошибка не оставляет частично импортированные записи. Оригиналы не изменяются.

| Поле старой схемы | Преобразование/правило |
| --- | --- |
| Session/profile `id` | UUID; origin + UUID — ключ идемпотентного импорта |
| `date`, `discoveredAt`, вложенный inspection.date | Число секунд от 2001-01-01 UTC с дробью; для Unix прибавить 978307200, не потерять дробную часть |
| Даты JSON/CSV-экспорта | ISO-8601; экспорт результатов не принимается молча за файл внутренней истории |
| `config` | Проверить все типы/лимиты; seed/index читать точно; отсутствие optional полей совместимо со старой схемой |
| `status` | Scanning/Starting/Authorizing/Stopping → Interrupted; **Interrupted → Interrupted**; Completed/Paused/Stopped/Failed/Ready отображаются в соответствующий enum; неизвестное значение не превращается в Completed |
| `hostnameStatus` | pending → not-checked; прочие известные значения сохраняются |
| results, inspection, evidence, log, percent | Сохранить значения/связи; дедупликация IP/port/protocol внутри сессии; неполные/неизвестные поля обрабатывать с отчётом |
| Pause checkpoint | Сохранить точно; доступность Resume отдельно проверяется по config и совместимости scanner |

Решение автора: повторный импорт уже импортированного UUID не перезаписывает новую
историю; неизменившаяся запись пропускается, изменившаяся отмечается конфликтом
в отчёте. Нет скрытого merge или дублирования. Отчёт: импортировано/пропущено/
конфликты/ошибки. Проверить даты 0 и дробные секунды, старые optional поля,
повторный импорт и сохранность количества/содержимого исходных результатов.

## 8. Производительность и жизненный цикл машины

Согласованные цели на 100 000 строк: p95 полного фильтра <100 мс и память
приложения ≤512 MiB. Это критерии, не уже полученные результаты.

Фиксированный синтетический набор для Slint: IP/port/protocol/time/service/
hostname/device/evidence, короткие и длинные строки. Release-сборка, одинаковая
машина, прогрев, 100 фиксированных запросов разной селективности. Время от
принятия фильтра до отображённого результата, включая debounce/model/bridge/render;
отчёт p50/p95/max. Проверяется idle и фоновой поток 1000 событий/с в течение 60 с
(методика автора, скорость событий не равна скорости пакетов masscan).

Бюджет памяти включает процесс приложения, UI/model, Rust core и принадлежащие
ему UI-процессы при тесте таблицы; внешние masscan/Nmap не входят в этот бюджет (Ред. 8 (норма): masscan теперь встроен в runner и измеряется вместе с ним; внешним остаётся Nmap),
их потребление и runner измеряются отдельно в интеграционном отчёте. Зафиксировать
RSS/платформенную сопоставимую метрику, baseline, peak загрузки/фильтра/обновлений
и отсутствие монотонного роста после циклов очистки. На каждой целевой машине
тест считается отдельно: быстрый Mac не подтверждает Windows/Ubuntu.

Решение автора: начальная доставка UI пакетами каждые 50 мс или по 1000 изменений;
одна постановка в UI event loop на пакет. Очередь ограничена 4 MiB сериализованных
событий плюс измеряемые overhead. Progress можно coalesce, результаты и lifecycle
events нельзя молча терять. При медленном UI данные остаются в SQLite, передаются
изменения модели/диапазоны. При невозможности записи ограничить буфер и остановить
скан с диагностикой неполноты. Backpressure stdout может влиять на scanner:
не обещать сохранность не полученных из сети ответов.

100k — нагрузка приёмки, не скрытый предел удаления результатов. 1M — отложенный
стресс-тест укрепления, не gate v1 и без обещания того же фильтра: нет OOM/crash/бесконечной очереди;
допустимы paged view или явная остановка при исчерпании ресурсов. Журнал ограничен
отдельно с отметкой усечения. Это инженерные проверки, не расширение v1 до big data.

| Событие | Поведение |
| --- | --- |
| Сон | Если возможно, остановить до сна; после пробуждения сверить процесс/состояние; не возобновлять автоматически; без подтверждения Interrupted |
| Смена сети/интерфейса/VPN | Прекратить попытку с явной причиной; проверять route/interface identity, а не только имя; новый старт пользователем |
| Disk full/ошибка записи | Не ACK checkpoint, не сообщать «сохранено», не заменять БД пустой; остановка при невозможности сохранить, явная неполнота |
| Crash UI/runner | Завершить scanner по §5.4; восстановить только committed данные; не показывать старое Scanning как живой скан |

Сон не гарантирует достаточно времени для graceful checkpoint. Отсутствие
новых находок не считается зависанием. После restart никакой scan не стартует сам.

## 9. Инструменты, версии, лицензии и сборки

> **Ред. 8 (история):** фраза «masscan и Nmap остаются внешними» (в части masscan), версия masscan 1.3.2 и матрица версий masscan, проверка параметров masscan, сравнение форматов вывода (`-oL`, `-oJ`, interactive) и запрет включать бинарники masscan в сборку. **Ред. 8 (норма):** Nmap остаётся внешним, Npcap устанавливает пользователь, матрица проверок Npcap и условия лицензии Nmap сохраняются. Перечисленное в «Ред. 8 (история)» это исторический Swift-эталон и не действует для встроенного rmasscan; остальной текст раздела остаётся в силе.

masscan и Nmap остаются внешними; Npcap на Windows пользователь устанавливает
самостоятельно по применимым условиям. UI диагностирует отсутствие/несовместимость,
а не скачивает или исправляет систему молча. Nmap `-sT -Pn` может работать без
Npcap, поэтому его требования не смешиваются с raw scanning masscan [S8].

Решение автора: первая проверка использует masscan 1.3.2 как исходную версию
поведения, но окончательная таблица поддержки состоит из реально проверенных
комбинаций OS + version/commit + hash + driver + capabilities. Не объявлять
все «>=1.3.2» совместимыми. На Windows фиксируется конкретная сборка, не просто
строка версии. Для Nmap 7.992 — известная проверка старой Mac-версии, не обязательный
минимум для остальных ОС. Минимально поддерживаемые версии получаются из матрицы
проверок до заявления поддержки; неподдерживаемый инструмент блокирует свою функцию.

Проверить без scan packets version/help/echo и нужные параметры. В runtime важны
interactive/status, seed/resume-index, адаптеры и XML Nmap; настоящая пауза
проверяется только экспериментом. Windows `\Device\NPF_{GUID}` должен приниматься
как один argv-аргумент, если соответствует обнаруженному адаптеру; инъекции и
неподтверждённые идентификаторы отклоняются. Unix-валидатор имён не универсален.

Решение автора о выводе: в прототипе scanner сравнить текущий interactive parser
с list-output (`-oL`, filename `-`) и отдельно прогресс stderr. Предпочесть
машинный построчный результат, если подтверждены немедленный flush, полные записи
и отсутствие смешивания вывода; иначе оставить проверенный version-specific
interactive adapter. JSON `-oJ` — не обязательство, завершённость JSON при паузе
нужно проверять. От выбранного формата не должен меняться контракт результата.

Лицензионная политика для прототипов (решение автора, без покупок):

- Историческая альтернатива Qt (не входит в текущую поставку): доступные LGPLv3 Core/Gui/Qml/Quick/Quick Controls, динамическая линковка;
  не добавлять GPL-only модули. Зафиксировать условия/версии, необходимые notices
  и возможность замены/relinking; динамическая линковка одна не выполняет всё [S9].
- Slint: рассматривать Royalty-free для desktop с требуемой атрибуцией, backend
  без Qt; условия конкретной версии включить в manifest [S10].
- masscan — AGPL-3.0, Nmap — NPSL; не включать их бинарники в нашу сборку. **[Ред. 8 (норма): к masscan не применяется. Порт rmasscan (AGPL-3.0-only) компилируется в runner, ответ пользователя 2026-10-23 «AGPL-3.0 принимается»; любая передача сборки третьим лицам требует выдачи исходников под AGPL (спека порта §8.1). К Nmap (NPSL) правило остаётся: его бинарник в сборку не включается.]**
- Npcap Free не перераспространять; OEM и silent installer не покупаются/не
  включаются. Ограничения использования Free также проверяются для masscan [S11].

Личная сборка не является решением о будущем публичном/коммерческом выпуске.
Перед таким выпуском нужен отдельный разбор условий. Подпись для выбранного
helper механизма и публичная Developer ID distribution — разные вопросы:
Developer ID не объявляется универсальным условием любого сессионного launcher.
Если исследуемый механизм требует недоступного сертификата, он не считается
готовым; платные ресурсы/постоянный daemon не добавляются автоматически [S12].

Результат v1: запускаемая `.app` macOS, Windows-каталог `.exe` + runtime libraries,
Ubuntu-каталог с приложением/runtime + инструкция явной установки доверенных
helper-файлов при необходимости. Полноценный installer/.deb не является
обязательным результатом личной v1. Привилегированный запуск не выполняется из
пользовательского FUSE/AppImage. Slint и Rust-зависимости фиксируются Cargo.lock;
Qt не является runtime-зависимостью приложения. Установка toolchain
и runtime указывается явно, а не скрывается в сборочной команде.

| --- | --- | --- |
| B: Windows Npcap raw I/O и pause/resume engine (Ред. 8 (норма); прежнее «Windows masscan» историческое) | Реальные pause/resume с доказательством продолжения исходного задания | Windows и трёхплатформенная v1 не готовы; функция не убирается |
| A1: Slint на Mac | Таблица 100k, поток, кликабельные ячейки/выбор, корректность и метрики | INCONCLUSIVE при недостатке данных; FAIL только по проверенному невыполненному критерию |
| A2: Slint после A1 | Windows/Ubuntu и платформенный минимум всех трёх ОС, одинаковые требования | Не начинать продуктовый UI до завершения обязательных проверок |
| R: runner | Bootstrap в модели угроз, lifecycle, checkpoint и отсутствие осиротевшего masscan | Не объявлять сканирование готовым на непрошедшей ОС |

A1: план 1–2 рабочих дня и резерв 1 день для Slint; A2 оценивается отдельно.
Перерасход учитывается как стоимость, не автоматический no-go. INCONCLUSIVE
требует дополнительной проверки. Подтверждённый FAIL означает доработку или
отдельное решение пользователя; молчаливый переход на Qt не допускается.
Выбор Slint уже сделан, но готовность таблицы и платформ требует A1 и A2.

### 10.3. План полной реализации и приёмка

После прохождения B, A1/A2 и подтверждения runner lifecycle подготовить
детальный план: независимое ядро, SQLite/import, runner, UI, DNS/Nmap/export,
платформенная упаковка. Инженерная структура описана в §11, но scaffolding
до разрешения не создаётся.

Готовность личной v1: весь паритет §4, функциональные/аварийные проверки, метрики
на трёх целевых ОС, три запускаемые сборки и инструкция. Нижняя граница macOS 14
требует отдельного smoke/compatibility прогона на 14; до него это заявленная цель,
а не подтверждённая поддержка по запуску на более новой macOS. Если среды 14 нет,
отчёт явно отмечает ограничение, не меняя согласованную минимальную ОС.
CI/build success отдельно от UI launch и реального scan/driver test.

## 11. Тесты, репозиторий и переход с Swift

> **Ред. 8 (история):** «Fake masscan», имитирующий вывод и pause/checkpoint внешнего процесса, и «Windows fake проверяет настоящий console event». **Ред. 8 (норма):** вместо них fake-адаптеры engine (в коде: ManualClock и fake `Tx`/`Rx`) и fake-ответчик; golden fixtures вывода masscan и paused.conf сохраняются как данные паритета. Перечисленное в «Ред. 8 (история)» это исторический Swift-эталон и не действует для встроенного rmasscan; остальной текст раздела остаётся в силе.

После разрешения новый код живёт в том же репозитории, отдельной ветке,
`cross-platform/`: Rust core/validation, runner, storage, выбранный UI-adapter,
UI assets, tests/fixtures. Swift Sources/Tests/Package.swift/scripts сохраняются
во время переноса; Qt/CXX-Qt и прямой CMake-проект не входят в выбранный UI.
Решение автора: единая будущая команда `cargo xtask build` из cross-platform
проверяет toolchain и вызывает нужные сборщики, ничего не устанавливая молча.
Команда и структура сейчас не существуют.

Golden fixtures выделяются из Swift-тестов и обезличенных наблюдений: вывод
masscan/progress, paused.conf, CSV, Nmap XML, Swift-даты и u64. Fake masscan
в непривилегированном harness имитирует частичные записи, CR/LF, поток, ошибки,
pause/checkpoint, зависание и аварийный выход. Windows fake проверяет настоящий
console event. Подмена executable — только у тестового harness, не production
runner с повышенными правами. Fake/CI не подтверждают raw sockets, UAC, polkit,
system DNS, настоящий driver или работу конкретного masscan.

Проверки: injection и лимиты, CSV-формулы, XML entities/oversize/wrong host,
URL hostname syntax, u64 и импорт, один экземпляр, права файлов, диск/сон/сеть,
протокол/ошибки/очереди, смерть runner, настоящие pause/resume. Тесты не зеркалят
реализацию, а проверяют наблюдаемый контракт и границы отказов.

На macOS новая версия во время проверок имеет отдельное имя/каталог данных,
чтобы не затереть установленную Swift. Переключение после паритета и импорта:
сверить результаты/профили/inspection/даты, экспорт, live scan и pause/resume;
сохранить старый app и исходные JSON. Новое хранилище не пишется обратно в Swift.
Откат возвращает старое приложение и его оригинальные данные; данные, созданные
только новой версией, остаются в SQLite/экспорте и не обещаются читаемыми Swift.
Долгосрочная поддержка двух UI не планируется; удаление rollback-копии — отдельное
действие, не часть автоматического перехода.
